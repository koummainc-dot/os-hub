# Inventory migration reconciliation and repeatability checks

**Status: read-only plan validation. No database connection, writes, or production changes.**

## Added
- `src/systems/inventory/migration-reconcile.js` compares source aggregate counts with planned normalized rows, verifies planned foreign-key references, flags duplicate primary keys and cross-workspace rows, and checks that every legacy event is retained either as an ownership event or an audit event.
- `tests/t_inventory_migration_reconcile.mjs` covers deterministic repeat planning, counts, orphaned references, and missing-row detection.
- The test is included in the package test command.

## How to use it
1. Call `planInventoryAggregateMigration(aggregate, { workspaceId, resolveId })` with the same durable ID map for every run.
2. Call `reconcileInventoryMigrationPlan(aggregate, plan)`.
3. Stop if either `plan.safeToApply` or `reconciliation.safeToApply` is false, or if warnings require review.
4. Run the same input through the planner twice and compare with `compareInventoryMigrationPlans(first, second)`. A deterministic result proves repeatable plan output only; it does not prove database-writer idempotency.
5. Before any writer exists, independently compare source counts and fingerprints with a read-only export from an isolated database. No such live comparison is performed by this module.

## Safety boundaries
- The reconciler only inspects in-memory source and planned rows. It does not connect to Supabase or execute SQL.
- Audit table identity values are generated by PostgreSQL, so those rows are checked for retention but not primary-key duplication at plan time.
- It does not override the need for SQL constraint checks, RLS testing, explicit actor attribution, and review of all migration warnings.
