# 13 — دليل تشغيل Project Workspace

هذا الدليل يشرح **صفحة المشروع نفسها** بعد فتح مشروع من Projects OS. الهدف ليس وصف أسماء التبويبات فقط، بل توضيح: ماذا يرى المستخدم، ماذا يعبئ، ماذا يحدث عند الحفظ، وإلى أين تنتقل البيانات، وكيف تتصل الطبقات ببعضها.

> مصدر هذا الدليل: تنفيذ Project Workspace الحالي في `src/systems/projects/screens_b.jsx` مع النماذج والمخزن والكيانات المرتبطة.

## 1. دورة الدخول إلى Project Workspace

المسار الأساسي:

`Projects → اختيار مشروع → Project Workspace`

داخل مساحة المشروع يظهر:
- اسم المشروع وحالته والقائد والتواريخ.
- زر الرجوع إلى قائمة المشاريع.
- زر **＋ إضافة** للسجلات التي يملك المستخدم صلاحية إنشائها.
- تغيير حالة المشروع.
- تعديل المشروع.
- أرشفة/استعادة المشروع.
- حذف المشروع إذا كانت الصلاحية تسمح.
- تنقل مجموعات Workspace.

### مجموعات Workspace الحالية

| المجموعة | التبويبات |
|---|---|
| نظرة عامة | نظرة عامة |
| التخطيط | الاكتشاف، المهام، المواصفات، المعالم، Roadmap / Timeline |
| الأهداف | الأهداف (OKR) |
| التسليم | المخرجات، العمل والوقت |
| الحوكمة | المخاطر، المشاكل، القرارات |
| المعرفة والمراجع | الاجتماعات، المراجع والملفات |
| المالية | الملف المالي |
| النتائج | الإنجازات، تحديثات المشروع |
| التعاون | الفريق، النشاط |

على الهاتف يوجد اختيار واحد للتبويب بدل قائمة التنقل الجانبية/الموسعة.

# 2. رأس المشروع

رأس المشروع هو نقطة التحكم الأساسية.

### البيانات المعروضة

- اسم المشروع.
- رمز القفل إذا كان المشروع Private.
- نوع المشروع.
- قائد المشروع.
- تاريخ البدء.
- الموعد المستهدف.
- حالة المشروع.

### الإجراءات

#### ＋ إضافة
يمكن أن يظهر للمستخدم حسب صلاحياته:
- مهمة جديدة.
- مخرج.
- مواصفة PRD.
- خطر.
- مشكلة.
- قرار.
- رابط أو مرجع.

الميزة المهمة هنا أن **المشروع الحالي يُستخدم كسياق السجل الجديد**؛ لا يحتاج المستخدم إلى إعادة اختيار المشروع من الصفر.

#### تغيير الحالة
يغير حالة المشروع من القائمة المتاحة، مع استبعاد الحالة الحالية وArchived من الاختيار المباشر.

#### تعديل
يفتح `ProjectForm` لتعديل بيانات المشروع.

#### أرشفة
ينقل المشروع إلى الحالة المؤرشفة دون فقد السجل.

#### استعادة
تظهر للمشروع المؤرشف وتعيده إلى الاستخدام.

#### حذف
متاح فقط عند امتلاك صلاحية الحذف.

# 3. Overview — نظرة عامة

هذه ليست شاشة إدخال تفصيلية؛ هي **لوحة تفسير المشروع**.

## 3.1 الصحة والتقدم

تعرض:
- Health Badge.
- عدد المهام المنجزة مقابل إجمالي المهام.
- Progress.
- أسباب حالة الصحة.
- سجل انتقالات الصحة.
- الموعد المستهدف.
- المهام المتأخرة.
- المخاطر المفتوحة.
- المخاطر العالية.
- المشاكل المفتوحة.
- المشاكل الحرجة.

### التفاعل

كل رقم مهم يمكن أن يكون رابطًا إلى العرض التفصيلي المناسب.

مثال:
- الضغط على المهام المتأخرة → Tasks مع فلتر Overdue.
- الضغط على المخاطر العالية → Risks مع فلتر High.
- الضغط على المشاكل الحرجة → Issues مع فلتر Critical.
- الضغط على الموعد → Timeline.
- الضغط على مهمة مرتبطة بسبب صحي → Task Sheet.

## 3.2 الوقت والتكلفة

يعرض:
- الوقت المقدر.
- الوقت الفعلي.
- نسبة الوقت.
- الميزانية المخططة.
- رابط الملف المالي الفعلي في Finance OS.

قاعدة مهمة:

**Projects لا ينشئ Ledger ماليًا من داخل هذه البطاقة؛ الملف المالي الفعلي موجود في Finance OS.**

## 3.3 Traceability

تعرض نسبة تغطية التتبع.

إذا وجدت مهام بلا مواصفة أو Discovery مرتبط:
- يظهر عددها.
- يمكن فتح Tasks مع هذه المهام فقط.

الغرض من البطاقة هو اكتشاف الفجوات، وليس مجرد عرض نسبة تجميلية.

## 3.4 الهدف والوصف

يعرض:
- `final_goal`
- `description`

بشكل نصي كامل.

## 3.5 المهام المتأخرة

يعرض جزءًا من المهام المتأخرة مع:
- اسم المهمة.
- موعدها.
- المسؤول.
- فتح Task Sheet.

# 4. Tasks — المهام

هذه هي طبقة التنفيذ اليومية داخل المشروع.

## ماذا تفعل هنا؟

تنشئ وتراجع وتعدل وتفلتر المهام التابعة للمشروع.

المهمة يمكن أن تكون:
- مهمة رئيسية.
- مهمة فرعية عبر `parent_task_id`.
- مرتبطة بـ PRD/Requirement.
- مرتبطة بـ Discovery.
- مرتبطة بهدف/مشروع وفق مسار OKR.
- لها وقت تقديري ووقت فعلي.
- لها مخرجات وروابط ونشاط.

## أهم قاعدة

لا تنشئ مهمة خارج المشروع ثم تحاول إصلاح السياق يدويًا إذا كنت تعمل داخل Workspace؛ إنشاء المهمة من رأس المشروع أو تبويب Tasks يجب أن يحافظ على `project_id` للمشروع الحالي.

## الفلاتر الخاصة التي يمكن الوصول إليها من Overview

### Overdue
يعرض المهام الورقية المتأخرة فقط.

### Unlinked
يعرض المهام التي لا ترتبط بمواصفة أو عنصر Discovery عندما تكون هذه هي فجوة التتبع المكتشفة.

---

# 5. Milestones — المعالم

المعلم ليس Task.

المعلم يمثل **التزامًا أو محطة رئيسية** في المشروع، بينما Task تمثل العمل المطلوب لتنفيذ شيء.

## الحقول

- اسم المعلم.
- تاريخ الاستحقاق.
- الحالة:
  - Planned
  - In Progress
  - Completed
- المسؤول.
- الوصف.
- المهام المرتبطة.

## مثال

**المعلم:** إطلاق النسخة الأولى

**الموعد:** 2026-12-01

**المسؤول:** قائد المشروع

**المهام المرتبطة:**
- إنهاء PRD.
- تنفيذ الواجهة.
- اختبار الصلاحيات.
- اختبار دورة البيانات.

### الحفظ

عند الحفظ:
1. يتأكد النظام أن المهام المختارة تنتمي للمشروع نفسه.
2. يحفظ `related_task_ids`.
3. يسجل Activity.
4. يظهر المعلم في قائمة المشروع.
5. يظهر في Roadmap إذا كان مؤرخًا.

### الأرشفة

الأرشفة لا تحذف المعلم. فقط تخرجه من Roadmap النشط.

---

# 6. Roadmap / Timeline

Timeline يجمع العناصر المؤرخة المهمة للمشروع.

حاليًا يعتمد على:
- المهام leaf tasks التي لديها `start_date` أو `due_date`.
- المعالم التي لديها `due_date`.

## كيف تستخدمه؟

إذا لم تظهر عناصر:
- أضف تاريخ بدء/استحقاق للمهام.
- أو أضف موعدًا للمعلم.

إذا كانت العناصر مؤرخة:
- يتم حساب نطاق زمني من أول تاريخ إلى آخر تاريخ.
- تظهر المعالم والمهام على المسار.
- يمكن فتح المهمة.
- يمكن الرجوع إلى إدارة المعالم.

### القاعدة

Timeline ليس مصدر الحقيقة للتواريخ؛ هو **عرض مشتق** من بيانات Tasks وMilestones.

---

# 7. PRDs — المواصفات

PRD يمثل مواصفة تنفيذية للمشروع.

المسار الصحيح:

**Project → PRD → Requirement → Task → Output**

## عند إنشاء PRD

يكون المشروع الحالي محددًا.

## Requirement

كل Requirement يجب أن يكون تابعًا لـ PRD محدد.

## Task

المهمة التي تنفذ Requirement تحمل:
- `prd_id`
- ويمكن أن تحمل `prd_requirement_id`

وبذلك نستطيع الإجابة عن:

> ما المهمة التي تنفذ هذا الشرط؟

ثم:

> ما المخرج الناتج من تنفيذ المهمة؟

## لماذا هذا مهم؟

لأن وجود PRD وحده لا يثبت التنفيذ.

والـTask وحدها لا تثبت أنها تنفذ Requirement معين.

والـOutput وحده لا يثبت أنه ناتج عن ذلك العمل.

التتبع الكامل هو الذي يربط الطبقات.

---

# 8. Outputs — المخرجات

المخرج هو النتيجة التي يمكن مراجعتها أو اعتمادها.

يمكن أن يرتبط بـ:
- Project.
- Task.
- PRD.
- Requirement.

## أمثلة

- ملف تصميم.
- تقرير اختبار.
- Build.
- رابط Preview.
- وثيقة.
- ملف CSV.
- ملف PDF.

## عند الإنشاء من Workspace

المشروع الحالي يكون السياق الأساسي.

ثم يمكن ربط المخرج بمهمة أو PRD/Requirement حسب الحالة.

## دورة المخرج

**إنشاء → ربط → رفع/تسجيل → مراجعة → اعتماد/رفض → تحديث/إعادة محاولة عند الحاجة**

حالة Storage/RLS النهائية ما زالت Release Gate منفصلة؛ لذلك توثيق الـworkflow لا يعني أن القبول الحي للتخزين قد أُثبت بالكامل.

---

# 9. Risks — المخاطر

المخاطر تجيب:

> ما الشيء الذي قد يمنع المشروع من الوصول إلى النتيجة؟

## الحقول الأساسية

- العنوان.
- المسؤول.
- Probability.
- Impact.
- Review Date.
- PRD إن وجد.
- Mitigation.
- Mitigation Task IDs.
- Notes.

## Risk Score

**Risk Score = Probability × Impact**

وتستخدم عتبة النظام لتحديد High Risk.

## مثال

**الخطر:** تأخر اعتماد Storage

Probability: 4

Impact: 5

Score: 20

Mitigation:
- إعداد اختبار Storage contract.
- تنفيذ اختبار RLS.
- تجهيز fallback واضح.

Mitigation Tasks:
- Test Storage upload.
- Test restore.
- Verify permissions.

## العلاقة المهمة

**Risk → Mitigation → Task**

المخاطر لا يجب أن تعيش كملاحظات منفصلة عن التنفيذ.

---

# 10. Issues — المشاكل

Issue تختلف عن Risk.

- Risk = شيء قد يحدث.
- Issue = مشكلة حدثت بالفعل أو أصبحت قائمة.

## الحقول الأساسية

- العنوان.
- المشروع.
- Severity.
- Owner.
- Discovered At.
- Task IDs.
- Description.

## مثال

Issue:

**"رفع Output يفشل بعد إعادة تحميل الصفحة"**

Severity:
Critical

Owner:
مسؤول Projects

Tasks:
- إعادة إنتاج الخطأ.
- إصلاح recovery.
- اختبار Create → Reload.

## العلاقة

**Issue → Repair Task**

وبعد إغلاق المشكلة يجب أن يكون هناك أثر تنفيذي يمكن تتبعه.

---

# 11. Decisions — القرارات

Decision تسجل قرارًا اتُخذ بدل أن يبقى داخل محادثة أو ملاحظة.

## الحقول

- العنوان.
- الحالة.
- تاريخ القرار.
- صاحب القرار.
- Decision Maker.
- PRD.
- Related Tasks.
- Related Issues.
- Related Risks.
- Related Discoveries.
- Rationale.
- Rejected Alternatives.
- Expected Impact.
- Superseded By عند الحاجة.

## مثال

**القرار:** استخدام Supabase Storage المجاني مع RLS بدل خدمة ملفات خارجية.

Rationale:
- تقليل الأنظمة.
- الحفاظ على Workspace ownership.
- تجنب تكلفة مبكرة.

Rejected Alternatives:
- خدمة ملفات خارجية.

Expected Impact:
- تبسيط إدارة الملفات.

## العلاقة

Decision ليست مجرد Note.

هي سجل يمكن أن يفسر:
- لماذا تغيرت المواصفة.
- لماذا اختير حل معين.
- لماذا رُفض بديل.

---

# 12. Discovery — الاكتشاف

Discovery هو مكان الأشياء التي اكتُشفت أثناء العمل قبل أن تتحول إلى عمل تنفيذي رسمي.

## الحقول

- Title.
- Type.
- Status.
- Impact Level.
- Owner.
- Projects.
- Objectives.
- Source Title.
- Source URL.
- Description.
- Insights.
- Proposed Solution.
- Dropped Reason.
- Resolution Note.

## المسار

Discovery يمكن أن يبدأ كـ:

**Inbox → Working → Resolved / Dropped**

ثم يتحول إلى مسار تنفيذي مناسب مثل:
- Task.
- PRD.
- Project.
- Issue.

## مثال

Discovery:

> "المستخدم يحتاج رؤية الفرق بين المهام المرتبطة بـPRD والمهام غير المرتبطة."

بعد التحقق:

→ يتحول إلى Requirement أو Task حسب القرار.

المهم أن التحويل يحتفظ بالتتبع بدل نسخ المعلومة بلا أصل.

---

# 13. Meetings — الاجتماعات

Projects يستهلك اجتماعات Knowledge المرتبطة بالسياق.

الهدف:

**Meeting → Follow-up → Task**

## مثال

اجتماع:

> مراجعة إطلاق Projects v5

خلال الاجتماع يظهر:

> "إضافة اختبار حقيقي للحسابين."

المتابعة تتحول إلى:

**Task: تنفيذ اختبار Owner/Admin/Viewer**

ثم تصبح المهمة جزءًا من المشروع.

Projects لا يعيد بناء نظام الاجتماعات الخاص بـKnowledge؛ بل يربط سياق المشروع بالمرجع الموجود هناك.

---

# 14. Resources — المراجع والملفات

هذا هو المسار المرئي الحالي للمراجع.

يمكن من رأس المشروع اختيار:

**＋ رابط أو مرجع**

وتسجيل المرجع داخل المشروع.

الاستخدام:

- وثيقة خارجية.
- رابط Preview.
- Repository.
- مرجع تصميم.
- مصدر بحث.
- ملف مرجعي.

الهدف هو إبقاء المرجع داخل سياق المشروع بدل وضعه في ملاحظة غير قابلة للتتبع.

---

# 15. Finance — الملف المالي

Project Workspace يعرض رابطًا إلى الملف المالي الفعلي في Finance OS.

وفي Overview يظهر:
- Budget Planned.
- Currency.
- رابط Finance.

## قاعدة ملكية البيانات

Projects يعرف أن للمشروع جانبًا ماليًا.

لكن Finance OS هو مالك:
- Ledger.
- Transactions.
- Financial Profile.
- البيانات المالية الفعلية.

لذلك لا ننشئ Ledger موازيًا داخل Projects.

## مثال

Project:

**إطلاق منتج جديد**

Budget Planned:
10,000 EGP

ثم يتم التعامل مع:
- المصروف الفعلي.
- الحركات.
- التقارير.

داخل Finance OS.

---

# 16. Work & Time — العمل والوقت

هذه الطبقة تجيب:

> كم قدرنا العمل؟ وكم استغرق فعليًا؟

Overview يعرض:
- Estimated.
- Actual.
- Time Ratio.

وتبويب Work هو مكان التفاصيل.

## مثال

Task:
"اختبار دورة البيانات"

Estimated:
120 دقيقة

Actual:
180 دقيقة

Time Ratio:

**150%**

هذه المعلومة مفيدة لتقييم التخطيط، وليس فقط تسجيل الوقت.

---

# 17. OKR — الأهداف

المسار:

**Objective → KR → Project → Task**

المشروع لا يعيش منفصلًا عن الهدف الأعلى عندما يكون جزءًا من Objective.

## مثال

Objective:

> إطلاق منصة Projects مستقرة

KR:

> 100% من دورة البيانات الأساسية تعمل دون فقد.

Project:

> Projects v5 Acceptance

Tasks:
- Create → Reload.
- Edit → Reload.
- Archive → Restore.
- Permissions test.

بهذا يمكن الانتقال من الهدف إلى التنفيذ.

---

# 18. People — الفريق

People يعرض أعضاء المشروع وسياق التعاون.

الصلاحية المرتبطة به هي:

`project.members`

ويجب أن تُستخدم لإدارة عضوية المشروع بدل إنشاء قائمة أعضاء منفصلة داخل كل تبويب.

البيانات المرتبطة بالمهام والمخاطر والمعالم وغيرها تشير إلى أعضاء الفريق بالهوية المناسبة.

---

# 19. Wins — الإنجازات

Wins تسجل النتائج الإيجابية المهمة.

مثال:

> تم اجتياز اختبار دورة البيانات الحقيقية دون فقد.

الغرض:
- تسجيل النتيجة.
- الحفاظ على أثر الإنجاز.
- استخدامه لاحقًا في Updates/Reviews.

Win ليست بديلًا عن Task أو Output.

---

# 20. Updates — تحديثات المشروع

Updates هي طبقة التواصل عن حالة المشروع.

يمكن استخدامها للإجابة:

> أين وصل المشروع؟

لكنها لا تستبدل:
- Task للحركة التنفيذية.
- Risk للمخاطر.
- Issue للمشكلة.
- Decision للقرار.
- Output للنتيجة القابلة للمراجعة.

### قاعدة النشر

عند وجود تحديث منشور ومثبت، لا نتعامل معه كمسودة عمل قابلة للتعديل بلا أثر؛ التغيير الجوهري يحتاج Update/Addendum حسب سياسة التحديث.

---

# 21. Activity — النشاط

Activity هو سجل الأحداث المرتبطة بالمشروع.

أمثلة:
- إنشاء Task.
- تعديل Task.
- إنشاء Risk.
- تحديث Milestone.
- أرشفة سجل.
- استعادة سجل.
- إنشاء Output.

الغرض:

**Activity = ماذا حدث؟**

وليس:

**Activity = أين أضع بيانات العمل؟**

لذلك لا يجب استخدام Activity كسجل بديل عن الكيانات الأساسية.

---

# 22. العلاقات الكاملة داخل Workspace

الصورة التشغيلية الأساسية:

**Project**
↓
**Tasks**
↓
**Outputs**

وبالتوازي:

**Project → PRD → Requirement → Task → Output**

والحوكمة:

**Project → Risk → Mitigation Task**

**Project → Issue → Repair Task**

**Project → Decision → Related Task / Risk / Issue / PRD / Discovery**

والاكتشاف:

**Project → Discovery → Task / PRD / Project / Issue**

والاجتماعات:

**Knowledge Meeting → Follow-up → Project Task**

والأهداف:

**Objective → KR → Project → Task**

والمالية:

# 24. مثال End-to-End كامل

## المرحلة 1 — الهدف

Objective:

> بناء Projects OS قابل للاعتماد.

KR:

> دورة البيانات الأساسية تعمل دون فقد.

## المرحلة 2 — المشروع

Project:

> Projects v5 Acceptance

يُحدد:
- الاسم.
- النوع.
- الأولوية.
- القائد.
- البداية.
- الموعد.
- الهدف النهائي.
- الوصف.
- الميزانية إن وجدت.

## المرحلة 3 — المواصفة

PRD:

> Data Lifecycle Acceptance

Requirement:

> يجب أن يستطيع المستخدم إنشاء مهمة ثم إعادة تحميل الصفحة مع بقاء البيانات.

## المرحلة 4 — التنفيذ

Task:

> اختبار Create → Reload

وتُربط بـ:
- Project.
- PRD.
- Requirement.

## المرحلة 5 — المخرج

Output:

> تقرير اختبار دورة البيانات.

يرتبط بالمهمة.

## المرحلة 6 — المشكلة

إذا فشل الاختبار:

Issue:

> البيانات لا تظهر بعد Reload.

ثم:

Repair Task:

> إصلاح persistence/reload.

## المرحلة 7 — القرار

Decision:

> اعتماد Repository API كمصدر الحقيقة.

ويرتبط بالمشكلة والمهمة والمواصفة عند الحاجة.

## المرحلة 8 — المعلم

Milestone:

> Acceptance Complete

ويرتبط بمهام الاختبارات النهائية.

## المرحلة 9 — النتيجة

Win:

> اجتياز دورة Create → Reload → Edit → Reload → Archive → Restore → Reload.

## المرحلة 10 — التحديث

Update:

> تم إغلاق دورة البيانات الأساسية مع بقاء اختبارات الحسابات المتعددة كـRelease Gate منفصل.

هذه هي الصورة التي تجعل Workspace **نظام تشغيل للمشروع** وليس مجرد مجموعة تبويبات.

# 25. قاعدة الاستخدام النهائية

عند العمل داخل Project Workspace اسأل أولًا:

**ما نوع المعلومة التي أريد تسجيلها؟**

ثم اختر الكيان الصحيح:

- عمل → Task
- نتيجة → Output
- تعريف → PRD / Requirement
- محطة → Milestone
- احتمال → Risk
- مشكلة → Issue
- قرار → Decision
- اكتشاف → Discovery
- اجتماع → Knowledge Meeting
- وقت → Work
- هدف → OKR
- عضو → People
- نتيجة إيجابية → Win
- تواصل → Update
- سجل حدث → Activity
- مال فعلي → Finance OS

والقاعدة الأهم:

> لا تستخدم سجلًا واحدًا لتعويض سجل آخر. استخدم العلاقات بينها حتى تظل Projects OS قابلة للتتبع من الهدف إلى العمل إلى النتيجة إلى القرار والمخاطر والمشاكل.
