# تقرير تنفيذ التكامل التوافقي — Travel OS

**الفرع:** `feat/sports-os-training-core`  
**النطاق:** تحسينات توافق داخل Travel فقط، دون تغيير قاعدة البيانات أو عقود Core المشتركة.

## ما أُضيف

- `src/systems/travel/integrations.js`: عقود اختيارية محددة للملفات والإشعارات والتقويم. لا يتم اعتبار الخدمة متاحة إلا إذا مرّر النظام واجهة كاملة بالعمليات المطلوبة.
- `createTravelIntegrationBridge(api, workspaceId)`: جسر موحد يستدعي فقط الخدمات التي يمررها Core صراحةً؛ لا يكتب مباشرةً في جداول/مخازن أنظمة أخرى.
- الجسر يرفض المراجع التي لا تطابق مساحة العمل، ويرفق `workspaceId` و`sourceSystem: "travel"` بالعمليات، ويستخدم مفاتيح مصدر ثابتة للتذكيرات وأحداث التقويم. الأخطاء تُعاد كحالة واضحة ولا تُبتلع على أنها نجاح.
- عمليات الملفات المتوقعة: `upload`, `getUrl`, `remove`. عمليات التذكير: `upsert`, `cancel`. عمليات التقويم: `upsert`, `remove`. الخدمة المشتركة نفسها مسؤولة عن التحقق النهائي من العضوية والصلاحيات، وعن idempotency.
- `travelSourceKey()`: معرّف ثابت لمصدر التكامل مبني على مساحة العمل ونوع السجل والمعرّف وموعد الاستحقاق.
- `buildTravelReminderReference()`: مرجع تذكير مستقر لموعد إلغاء الحجز أو انتهاء المستند، دون إرسال إشعار بذاته.
- `buildTravelCalendarReference()`: مرجع برنامج رحلة يحتوي على التاريخ والوقت والمكان والمنطقة الزمنية المعروفة؛ لا ينشئ حدثًا بذاته.
- صفحة إعدادات Travel تعرض حالة عقود الملفات والتذكيرات والتقويم بدل افتراض وجودها.
- تغييرات السجلات الأساسية (إنشاء/تعديل/حذف وتحديث التجهيز) تنشر حدثًا محدود البيانات `travel.record.changed` عبر ناقل `integrationEvents.js` الموجود، مع معرف مصدر ثابت ومعرف السجل فقط؛ لا تُرسل تفاصيل الحجوزات أو المستندات.
- رأس Travel يوضح مصدر البيانات الفعلي. عند fallback إلى localStorage يظهر تحذير أن البيانات قديمة أو غير متزامنة، بدل وصفها بأنها متصلة بالخادم.
- `tests/t_travel_integrations.mjs` يغطي ثبات المفاتيح، والتحقق من المدخلات، ومراجع التقويم، وعدم اعتبار الواجهة الجزئية خدمة جاهزة، ورفض اختلاف مساحة العمل، ومعالجة أخطاء الخدمات الاختيارية.
- تمت إضافة اختبار التكامل إلى أمر `npm test`.

## حدود الربط الفعلي

- **لم يتم العثور على خدمات Core Files / Notifications / Calendar مشتركة موصولة في الـAPI الذي يمرره التطبيق إلى Travel.** لذلك الجسر جاهز للتوصيل لكنه لا يجعل الخدمات متاحة تلقائيًا؛ تظل الحالة «غير متاحة» إلى أن يمرر Core تنفيذًا معتمدًا.
- لم يتم استخدام مخزن `knowledge-attachments` لملفات السفر، ولم تُنشأ قاعدة بيانات أو bucket جديدة.
- لم تُرسل إشعارات مشتركة ولم تُنشأ أحداث Calendar؛ إنشاء بيانات بديلة داخل Travel أو كتابة مباشرة في نظام آخر سيخالف ملكية البيانات ويعرّض النظام للتكرار.
- لا يدّعي adapter أن مراجع `storageNote` و`mediaPath` ملفات مرفوعة أو قابلة للفتح.
- أحداث `integrationEvents.js` محلية/أفضل جهد وليست ناقلًا خادميًا دائمًا؛ المستهلكون يجب أن يعيدوا قراءة السجل ويطبقوا idempotency ولا يعتبروا الحدث إشعارًا أو حدث تقويم.
- لم يُضف طابور مزامنة ثانٍ. واجهة `workspace_data` الحالية تخزن نسخة محلية لكنها لا تقدم طابور replay موثوقًا لهذا النظام؛ لذلك لا تُعرض النسخة المحلية كحفظ خادمي مؤكد.

## استعادة المزامنة المحلية بأمان

- أُضيف `src/systems/travel/offlineQueue.js` بطابور محلي واحد خاص بمساحة Travel، مع نسخة بيانات كاملة ووقت الحفظ المحلي وإصدار الخادم الذي بُني عليه التعديل.
- عند فشل الحفظ، يحاول Travel حفظ نسخة محلية للمراجعة ويظهر تنبيهًا صريحًا بأنها غير مؤكدة الخادم. عند وجود تعديل محلي معلّق، يمنع حفظ تغييرات إضافية حتى تُفحص الحالة.
- أُضيف إجراء يدوي «فحص الخادم / محاولة مزامنة آمنة»، مع تنزيل نسخة JSON لاسترداد التعديل المحلي بعد تأكيد تحذير الخصوصية. لا يعيد إرسال النسخة إلا عندما يكون إصدار الخادم معروفًا ومطابقًا تمامًا للإصدار الذي بُني عليه التعديل.
- إذا تغير إصدار الخادم، يحتفظ Travel بالنسخة المحلية ويعرض تعارضًا دون دمج تلقائي أو الكتابة فوق الخادم. إذا لم يوجد إصدار خادم معروف، يتطلب استردادًا يدويًا بدل استخدام upsert غير مشروط.
- أُضيف `tests/t_travel_offline_queue.mjs` إلى `npm test`. الاختبارات تغطي منطق الطابور، لكنها لا تثبت سلوك الشبكة الفعلي في المتصفح.
- **الحدود:** الطابور خاص بهذا المتصفح ومساحة العمل؛ ليس مزامنة خلفية أوفلاين متعددة الأجهزة. يلزم اختبار متصفح حقيقي وانقطاع شبكة وتعارض مستخدمين قبل اعتبار الميزة جاهزة إنتاجيًا.

## التحقق المطلوب

1. تشغيل `npm test` و`npm run lint` و`npm run build` على الفرع بعد هذه التغييرات، ومراجعة نتائج GitHub Actions قبل ادعاء نجاحها.
2. اختبار حفظ/إعادة تحميل فعلي مع انقطاع الشبكة؛ يجب مراجعة سلوك `workspace_data` الحالي قبل إعلان مزامنة أوفلاين مكتملة.
3. لاختبار الملفات: توصيل عقد Core Files معتمد واختبار الوصول بحسابين وصلاحيات مختلفة.
4. لاختبار الإشعارات والتقويم: توصيل APIs المشتركة مع upsert/delete idempotent واختبار منع التكرار.

**الحالة الحالية:** جسر تكامل fail-closed وعقود اختبار، وليس تكاملًا إنتاجيًا كاملًا مع الخدمات المركزية. لم تُنقل بيانات، ولم تُعدّل Supabase، ولم يُدمج PR ولم يُنشر التطبيق.
