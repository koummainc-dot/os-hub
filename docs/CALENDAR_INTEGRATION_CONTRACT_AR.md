# Calendar Integration Contract — عقد تكامل التقويم الموحد

> حالة الوثيقة: عقد معماري مقترح داخل OS Hub، وليس Calendar OS منفذًا أو جدولًا قائمًا. لا تُنشأ سجلات تقويم فعلية قبل اعتماد مالك التقويم وتطبيق مخزن موحد وصلاحياته.

## 1. الهدف وحدود المسؤولية

التقويم واجهة زمنية موحدة لعرض:
- **موعد مخطط**: شيء ينوي المستخدم فعله في وقت مستقبلي.
- **حدث فعلي**: شيء وقع بالفعل، مصدره النظام الذي يملك سجل الحقيقة.
- **تذكير**: تنبيه مرتبط بموعد أو سجل، وليس سجل نشاط مستقلًا.
- **عنصر طوال اليوم / فترة**: حدث له تاريخ أو نطاق زمني دون ساعة محددة.

لا يملك Hobbies OS أو Habit OS أو Projects OS تقويمًا موازيًا. كل نظام يحتفظ بسجلاته الأصلية، ويعرض التقويم نسخة مرجعية قابلة للتنقل إلى سجل المصدر.

## 2. مالك البيانات

- Calendar (عند تنفيذه) يملك فقط بيانات الموعد والتذكير والتفضيلات الزمنية.
- Hobbies يظل مالك جلسات الممارسة المكتملة وخطط الممارسة الخاصة بالهواية.
- Habit يظل مالك العادات وسجلات تنفيذها.
- Projects يظل مالك المهام والمواعيد النهائية المرتبطة بالمشروع.
- أي تعديل في موعد مشتق يجب أن يعود إلى النظام المصدر عبر عقد كتابة مصرح؛ لا تُعدّل نسخة العرض مباشرة.

## 3. شكل الحدث الموحد

الحقول المنطقية المقترحة:
- `id`: UUID خاص بعنصر Calendar.
- `workspace_id`: مساحة العمل.
- `title`, `description`.
- `kind`: `appointment | task_due | practice_plan | reminder | all_day`.
- `status`: `scheduled | completed | cancelled | skipped`.
- `starts_at`, `ends_at`: توقيت UTC بصيغة timestamptz؛ كلاهما مطلوب للموعد ذي الوقت، و`ends_at > starts_at`.
- `local_date`: تاريخ محلي للأحداث طوال اليوم أو السجلات التي يملك مصدرها تاريخًا محليًا.
- `timezone`: اسم IANA صريح مثل `Africa/Cairo`، ولا يُستنتج من UTC.
- `source_system`, `source_collection`, `source_record_id`: مرجع سجل الحقيقة.
- `source_version` أو `source_updated_at`: كشف النسخ القديمة.
- `idempotency_key`: فريد لكل مساحة عمل ومصدر.
- `created_by`, `created_at`, `updated_at`.

## 4. الفصل بين النشاط والموعد

- `hobbies.practice_session.completed` يظل حدث نشاط فعليًا؛ لا يتحول تلقائيًا إلى موعد.
- خطة ممارسة أسبوعية في Hobbies لا تصبح موعدًا يوميًا إلا بعد إنشاء occurrences صريحة وموافقة المستخدم.
- عند إكمال موعد ممارسة، لا ينشئ Calendar جلسة Hobbies ثانية. يرسل أمرًا للنظام المصدر أو يربط بالجلسة الأصلية.
- إلغاء الموعد لا يحذف سجل ممارسة مكتملًا.
- تذكير الموعد لا ينشئ مهمة جديدة ما لم يطلب المستخدم ذلك.

## 5. التكرار والاستثناءات

عند تنفيذ التكرار لاحقًا:
- تخزين قاعدة التكرار (RRULE) في سجل السلسلة، مع `series_id`.
- كل occurrence لها هوية مستقرة ومفتاح idempotency.
- الاستثناءات والإلغاء الجزئي تحفظ كاستثناءات، ولا تعيد توليد سجلات سابقة.
- حدود التوليد الزمنية تكون نافذة مستقبلية محددة؛ لا يتم توليد عدد غير محدود من المواعيد.

## 6. الخصوصية والصلاحيات

- قراءة عنصر Calendar تتطلب صلاحية Calendar، إضافة إلى صلاحية قراءة المصدر إذا كان العنصر يعرض تفاصيل مصدر محمي.
- العناصر الخاصة تتبع `visible_to` على مستوى السجل؛ لا يكفي حقل نصي مثل `privacy: private`.
- عمليات الكتابة والتحويل إلى مصدر تتطلب صلاحية تعديل النظام المالك.
- لا تكشف إشعارات الأجهزة عنوانًا أو وصفًا حساسًا قبل التحقق من صلاحية المستخدم.
- التذكيرات لا تتجاوز حدود الصلاحيات بعد سحب الوصول أو حذف العنصر.

## 7. عقود الربط

| المصدر | ما يعرضه Calendar | ما لا يفعله Calendar |
|---|---|---|
| Hobbies | مواعيد ممارسة مخططة عند اعتمادها، وسجل جلسة كمعلومة تاريخية | لا ينشئ جلسة مكتملة مكررة |
| Habit | مواعيد العادة أو تذكيراتها بعد وجود Habit runtime | لا ينشئ Daily Log مكررًا |
| Projects | تواريخ الاستحقاق ومواعيد المشروع | لا يصبح مالك المهمة أو حالة إنجازها |
| Learning | جلسات دراسة مخططة ومواعيد الدروس | لا يكرر سجل الدراسة المكتمل |

## 8. دورة حياة المزامنة

1. النظام المصدر يحفظ سجله الأصلي.
2. يصدر حدثًا بمعرف المصدر وإصدار السجل ومفتاح idempotency.
3. Calendar ينشئ/يحدث projection فقط إذا كان المصدر مخولًا.
4. حذف المصدر أو إلغاءه ينتج tombstone/حالة ملغاة، لا حذفًا صامتًا.
5. المستهلك يعالج التكرار بأمان، ويحتفظ بسجل أخطاء/إعادة محاولة.
6. لا يُعلن نجاح المزامنة قبل تأكيد الخادم.

## 9. شروط البدء بالتنفيذ

- اعتماد Calendar كقسم مستقل في سجل الأنظمة والصلاحيات.
- اعتماد مالك المواعيد والـ schema النهائي.
- Migration ومخزن موحد مع RLS واختبارات مستخدمين متعددين.
- واجهة عرض شهر/أسبوع/يوم مع timezone وDST.
- اختبارات idempotency، التكرار، إلغاء المصدر، سحب الصلاحية، وتعارض الكتابة.
- عدم إنشاء مواعيد تلقائية من بيانات قديمة دون موافقة المستخدم.

## 10. قرار المرحلة الحالية

تم تثبيت العقد فقط. لا توجد شاشة Calendar، ولا جدول Calendar، ولا مواعيد أو تذكيرات فعلية منشأة من Hobbies. تبقى جلسات الممارسة أحداثًا تاريخية في Today.
