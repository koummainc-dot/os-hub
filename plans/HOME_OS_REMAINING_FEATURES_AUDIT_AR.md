# Home OS — جرد الميزات غير المكتملة قبل التنفيذ
تاريخ الجرد: 2026-10-31
الفرع: `feat/home-os-phase1-foundation`
PR: #95 — Draft وغير مدمج

> هذا المستند يفرّق بين ما يظهر في الواجهة، وما تدعمه طبقة البيانات فعليًا، وما لم يُنفّذ بعد. الجرد مبني على ملفات الفرع الحالي، ولا يعني أن الميزات اجتازت اختبارات قبول أو أنها منشورة. لم تُنفذ أي كتابة على Supabase ولم تُطبق migrations.

## الحالة الحالية بعد التنفيذ (تحديث 2026-10-31)

### نُفّذ في الفرع
1. **حماية Home Repository:** يمنع الرجوع الصامت إلى الكتابة في `workspace_data/localStorage` عندما يكون مسار الحفظ العلائقي غير متاح.
2. **استلام مشتريات ذري:** Migration `20261031180000_home_os_atomic_purchase_receipts.sql` تضيف سجل الإيصال وبنوده وRPC واحدة تُحدّث الطلب وبنوده والمخزون وحركة المخزون وAudit وOutbox داخل معاملة واحدة. مفاتيح idempotency تمنع إعادة تطبيق الإيصال، بما في ذلك إعادة محاولة الإيصال النهائي بعد أن تصبح الحالة `received`.
3. **تكامل واجهة الاستلام:** `src/core/core.js` و`src/systems/home/operations.jsx` يستدعيان RPC الذرية في الوضع الحقيقي، ثم تُحدّث واجهة المخزون الرئيسية بإعادة القراءة من المستودع. الديمو يحتفظ بمساره المحلي المنفصل.
4. **عمليات علائقية:** Migration `20261031190000_home_os_relational_operations.sql` تضيف الفواتير ودورات الاستحقاق والمدفوعات، وتحوّل القراءة إلى الجداول العلائقية عند وجود بيانات، مع fallback قراءة للـ snapshot القديم. الحفظ يكتب الجداول التشغيلية والـ snapshot التوافقي داخل معاملة RPC واحدة؛ لا توجد كتابة مستقلة من المتصفح إلى كل مخزن.
5. **أحداث دائمة:** حفظ المهام والإنجازات والصيانة والفواتير يضع الأحداث المرسلة ضمن `home_outbox_events` داخل معاملة الحفظ. إيصالات الشراء تُنشئ حدث Outbox مباشرة داخل معاملة الاستلام. اعتماد المعاملات المالية النهائية لا يزال يدويًا.
6. **تعارض الجلسات:** Migration `20261031200000_home_os_operations_concurrency.sql` تضيف `home_operations_load_v2/save_v2`، وقفلًا على مستوى مساحة العمل، ورفضًا لنسخة قديمة برسالة `HOME_OPERATIONS_CONFLICT`. الواجهة تعرض رسالة واضحة بدل استبدال تحديث أحدث بصمت.
7. **حماية سجل الشراء:** تمنع الواجهة حذف بند سبق استلامه، ويحمي قيد المفتاح الأجنبي سجل الإيصالات من الحذف.

### التحقق الآلي
- **Home OS SQL smoke:** نجح في بيئة PostgreSQL مؤقتة على GitHub Actions بعد إضافة migration الذرية والعمليات العلائقية والتزامن. الاختبار يغطي الاستلام الجزئي والنهائي، تكرار الطلب، حركات المخزون، Outbox، الفواتير والمدفوعات، قراءة الجداول العلائقية، ورفض الكتابة بنسخة قديمة.
- **CI / Verify app:** كانت اختبارات البناء والتطبيق تمر على commit سابق قريب من هذه التغييرات؛ يجب اعتماد نتيجة التشغيل الأحدث قبل اعتبار كل التعديلات الحالية مكتملة.
- لم تُطبّق أي Migration على Supabase الإنتاجية، ولم يُدمج PR #95.

### ما يزال ناقصًا ويمنع اعتبار Home OS مكتملًا نهائيًا
| المجال | الحالة الحالية / المطلوب |
|---|---|
| عقارات وغرف ومخزون | لا تزال واجهات هذه الكيانات تعتمد على Snapshot RPC؛ يلزم نقلها إلى أوامر علائقية ذرية، ومنع تعديل الكمية خارج دفتر الحركات، واختبار التعارض. |
| إنهاء نسخة Snapshot للعمليات | ما زال `home_operations_snapshot` مرآة توافقية وfallback للبيانات القديمة؛ يلزم تقرير مصالحة للبيانات التاريخية، ثم إزالة المرآة بعد إثبات عدم وجود مستهلك قديم. |
| تسليم Outbox | الأحداث تُحفظ دائمًا، لكن لا يوجد بعد عامل خادمي يطالب بالأحداث ويعيد تسليمها إلى Finance/Today مع retries وdead-letter؛ حدث المتصفح ما زال أفضل جهد وليس ضمان تسليم متعدد الأجهزة. |
| صلاحيات العقار والغرفة | لا توجد عضوية منزلية وصلاحيات view/edit على مستوى العقار/الغرفة مع RLS واختبارات عزل بين الأعضاء. |
| التذكيرات الخلفية | التذكير الحالي يعمل أثناء فتح التطبيق؛ لا يوجد scheduler/push delivery موثوق بعد إغلاقه. |
| الفواتير | أصبحت الفاتورة والاستحقاقات والمدفوعات علائقية؛ ما زال يلزم توسيع واجهة سجل الدفعات/الدورات واختبارات قواعد التكرار المتقدمة. |
| المخزون الذري | الاستلام المرتبط بالشراء ذري، لكن حركات المخزون العامة وتعديل الكمية لا تزال تحتاج RPCs نطاقية تمنع تعديل الرصيد دون حركة موثقة. |
| اختبارات القبول | لا تزال اختبارات المتصفح end-to-end، والتزامن بين جلستين حقيقيتين، وصلاحيات العقار/الغرفة، وإعادة تسليم Outbox غير مكتملة. |
| ترحيل البيانات | يلزم dry-run ومصالحة counts/relationships/hash للـ snapshot القديم في بيئة معزولة قبل حذف أي fallback أو التفكير في النشر. |

> لذلك: **تم تنفيذ أساس علائقي مهم واختبارات SQL ناجحة، لكن القسم ليس جاهزًا للدمج النهائي بعد.** الخطوة التالية ذات الأولوية: إكمال حركات المخزون الذرية، ثم Outbox dispatcher، ثم صلاحيات النطاق والتذكيرات الخلفية، ثم اختبارات القبول ومصالحة الترحيل.

## سجل التنفيذ بعد الجرد

### الخطوة 1 — منع الرجوع الصامت إلى مسار الكتابة القديم
- الحالة: نُفذت في الفرع، وتحتاج تشغيل الاختبارات في بيئة المشروع للتحقق.
- الملف: `src/systems/home/repository.js`.
- التغيير: إذا كانت واجهة `saveNormalizedHome` موجودة لكن RPC غير متاحة أو لم يؤكد الخادم نجاحها، يفشل الحفظ برسالة `HOME_NORMALIZED_STORAGE_REQUIRED` بدل استدعاء `api.save` الذي يكتب إلى `workspace_data` و`localStorage`.
- التوافق: أبقينا fallback للقراءة القديمة مؤقتًا، وأبقينا adapter الاختبارات/الديمو الذي لا يعرّف أصلًا `saveNormalizedHome` منفصلًا.
- اختبار مضاف: `tests/t_home_domain.mjs` يتحقق من عدم استدعاء الحفظ القديم عند غياب RPC العلائقية، ومن استمرار مسار الحفظ العلائقي عند نجاحه.
- التحقق: راجعت وجود التعديل والاختبار في الفرع. لم تتوفر نتيجة CI مرتبطة بهذه الـ commits وقت التحديث؛ لذلك لا يُسجل الاختبار على أنه ناجح حتى يُشغّل فعليًا.
- الحدود: هذا التغيير لا يحوّل عمليات Home OS إلى CRUD علائقي ولا يحل ذرية الاستلام الجزئي أو تزامن العمليات. تلك خطوات تالية منفصلة.

## ملخص تنفيذي

**القرار الحالي:** تحولت عمليات المهام والصيانة والمقدّمين والمشتريات والفواتير إلى قراءة/كتابة علائقية عند وجود سجلات، مع حفظ توافقي مؤقت ونسخة توافقية للبيانات القديمة. الاستلام الجزئي والنهائي أصبحا عملية خادمية ذرية، وأُضيفت سجلات Outbox وفواتير/استحقاقات علائقية وتحقق نسخة متفائلة. تبقى كيانات العقارات والغرف والمخزون العام وبعض مسارات التكامل/الصلاحيات/التذكيرات بحاجة إلى إكمال قبل القبول النهائي. راجع قسم «الحالة الحالية بعد التنفيذ» باعتباره المرجع الأحدث؛ الجدول التالي هو خط الأساس الذي سبق هذه التغييرات.

## 1. مصفوفة الميزات حسب الحالة

الحالات:
- **موجودة مبدئيًا:** واجهة/منطق مجال موجود، لكن يلزم ربطه بالبيانات الدائمة واختبارات القبول.
- **جزئي:** جزء من المسار موجود مع فجوة وظيفية أو تقنية تمنع الاعتماد.
- **غير منفذ:** لا يظهر تطبيق فعلي مكتمل في ملفات الفرع التي تمت مراجعتها.

| الميزة | الحالة | الفجوة التي تمنع الاعتماد |
|---|---|---|
| العقارات والغرف والإعدادات | موجودة مبدئيًا | تُقرأ وتُكتب عبر Snapshot RPC؛ يلزم نقلها إلى عمليات repository واضحة مع منع الاستبدال الكامل والتعارض بين الجلسات. |
| المخزون وحركاته | جزئي | الحركة والكمية تُحدّثان من الواجهة ثم تحفظان ضمن Snapshot؛ لا توجد RPC نطاقية ذرية لكل حركة، وتظل إمكانية تعديل الكمية مباشرة منفصلة عن سجل الحركات. |
| المهام المنزلية | موجودة مبدئيًا | CRUD والحالات والتكرار في الواجهة، لكن التخزين Snapshot كامل؛ لا توجد عملية خادمية ذرية لتسجيل الإنجاز وتحديث المهمة وتوليد الحدث. |
| سجل إنجازات المهام | جزئي | يوجد `completions` داخل JSON snapshot، لا جدول دائم مفعّل في مسار الواجهة؛ مفتاح idempotency يُنشأ لكل ضغطة ولا يمنع وحده تكرار الطلبات المنطقية. |
| المهام المتكررة | جزئي | حسابات المجال موجودة، لكن إنشاء/توليد occurrences المجدولة وتفادي تكرار occurrence في الخادم غير مكتملين. |
| الصيانة | موجودة مبدئيًا | سجلات الصيانة محفوظة في Snapshot رغم وجود جدول علائقي؛ تحديث الحالة والتكلفة وإرسال حدث Finance منفصلان. |
| مقدمو الخدمات | موجودة مبدئيًا | CRUD في Snapshot، بينما الجدول العلائقي موجود لكنه غير مستخدم كمسار الحقيقة من الواجهة. |
| طلبات الشراء وبنودها | جزئي | حالات دورة الشراء وبنود متعددة موجودة، لكن بيانات الطلب والبنود محفوظة في Snapshot ولا توجد قيود علائقية فعالة في المسار الحالي. |
| الاستلام الجزئي | غير مكتمل تقنيًا | تُحدّث حركة المخزون أولًا ثم كمية الاستلام وحالة الطلب في حفظ منفصل. الانقطاع/التزامن قد يترك المخزون والطلب غير متطابقين. |
| منع تكرار الاستلام | جزئي | المفتاح الحالي مشتق من كمية الاستلام السابقة، لكنه يُحسب في الواجهة؛ لا يوجد قفل/تحقق خادمي موحد يضمن idempotency للطلب والبند وحركة المخزون والإيصال معًا. |
| إيصالات الاستلام | غير منفذ ككيان دائم | لا يوجد سجل إيصالات مستقل يتيح تاريخ كل دفعة استلام وكميتها وتكلفتها وفاعلها؛ المعلومات موزعة بين كمية مستلمة وحركة مخزون وحدث متصفح. |
| الفواتير الدورية | موجودة مبدئيًا | منطق حساب التواريخ موجود، لكن الفاتورة وحالات الدفع محفوظة داخل Snapshot؛ لا يوجد سجل دفعات/Occurrences مستقل لكل دورة. |
| تقارير المنزل | جزئي | مؤشرات مبنية على بيانات الواجهة الحالية، ولا توجد طبقة تقارير علائقية قابلة للتحقق أو تدعم التاريخ والتجميع عبر الفترات. |
| ربط تكاليف Home مع Finance | جزئي | الأحداث تنشر بعد الحفظ من المتصفح؛ لا يوجد outbox دائم. يحتاج المستخدم إلى مراجعة الاقتراح المالي قبل إنشاء الحركة، وهذه المراجعة اليدوية يجب أن تبقى. |
| إنجازات Home في Today | جزئي | حدث المتصفح/LocalStorage لا يضمن ظهور الحدث في جلسة أو جهاز آخر، ولا توجد آلية إعادة تسليم دائمة. |
| Outbox دائم | غير منفذ | لا يوجد جدول أحداث دائم مع حالة التسليم، ومحاولات الإعادة، والتأخير، وdead-letter، وقيد يمنع تكرار الحدث. |
| إدارة أعضاء المنزل | غير منفذ | الواجهة تستقبل أعضاء مساحة العمل لتعيين المهمة؛ لا توجد عضوية منزل مستقلة مع دعوات/إزالة/حالة عضوية وتحديد العقارات المتاحة لكل عضو. |
| صلاحيات العقار والغرفة | غير منفذ | الصلاحيات الحالية على مستوى Home/المساحة؛ لا توجد صلاحيات view/edit على مستوى العقار أو الغرفة مع اختبار منع الوصول المتقاطع. |
| التذكيرات أثناء فتح التطبيق | موجودة مبدئيًا | تستخدم `setInterval` وNotification API في المتصفح، وتحتاج التطبيق مفتوحًا. |
| الإشعارات الخلفية | غير منفذ | لا يوجد scheduler خادمي أو queue أو push/background delivery بعد إغلاق المتصفح. |
| سجل التدقيق | جزئي | يوجد جدول تدقيق في مخطط المرحلة الأولى، لكن لا تسجل كل العمليات الحساسة كسجلات دائمة موحدة، كما أن حفظ Snapshot لا يوفر تفاصيل كل تغيير. |
| إدارة التعارض بين الجلسات | غير منفذ | `home_operations_save` يستبدل JSON كاملًا ويزيد version دون اشتراط version متوقع؛ لا توجد optimistic concurrency أو معالجة merge/conflict على مستوى السجل. |
| استمرار البيانات بين الجلسات | جزئي | يعتمد على توفر migrations وRPCs؛ يوجد fallback عام في API إلى `workspace_data` وlocalStorage، ويجب ألا يُستخدم هذا المسار ككتابة بديلة لبيانات Home الحية. |
| نقل البيانات القديمة | غير منفذ | لا يوجد dry-run/migration reconciliation يحدد مصدر كل سجل، التكرارات، المفقودات، أعداد السجلات، أو hash/report قبل التحويل. |
| اختبارات RLS | جزئي | يوجد smoke test محدود لـ view/edit وعزل workspace في قاعدة اختبار محلية؛ يلزم اختبارات شاملة للأدوار والجداول والـ RPCs، خاصة العقار/الغرفة والعضوية. |
| اختبارات التزامن وإعادة المحاولة | غير منفذ | لا توجد اختبارات قبول متزامنة لطلبَي استلام، أو حفظين متعارضين، أو إعادة محاولة بعد نجاح جزء وفشل الجزء الآخر. |
| اختبار متصفح end-to-end | غير منفذ | لا يظهر اختبار متصفح كامل لدورة إنشاء الطلب ثم استلام جزئي ثم تحديث المخزون ثم ظهور اقتراح Finance/Today واستمرار البيانات بعد إعادة التحميل. |
| فشل/استعادة الاتصال | جزئي | رسائل خطأ موجودة، لكن لا توجد سياسة موحدة للـ retry الآمن، كشف تعارض النسخ، إعادة إرسال Outbox أو حالة مزامنة واضحة للمستخدم. |

## 2. الجرد المعماري الذي يجب أن يحكم التنفيذ

### مصدر الحقيقة ومسارات التخزين
1. `src/systems/home/repository.js` يحاول `loadNormalizedHome/saveNormalizedHome` ثم يرجع إلى `api.load/api.save` إذا لم تكن RPC متاحة.
2. `src/core/core.js` يربط Home بالمكالمات `home_load_snapshot/home_save_snapshot`، ويربط العمليات بـ `home_operations_load/home_operations_save`.
3. `api.load/api.save` العامان يقرآن/يكتبان `workspace_data` ويستخدمان `localStorage` كمسار fallback/cache؛ يجب ألا يكون هذا fallback مصدر كتابة بديلًا للبيانات التشغيلية الحية.
4. `20261031140000_home_os_phase1_foundation.sql` ينشئ `home_settings`, `home_properties`, `home_rooms`, `home_inventory_items`, `home_inventory_movements`, `home_audit_log`.
5. `20261031160000_home_os_phase2_operations.sql` ينشئ جداول المهام والإنجازات ومقدمي الخدمات والصيانة وطلبات الشراء وبنودها.
6. `20261031170000_home_os_operations_snapshot.sql` يخزن عمليات Home ككائن JSONB كامل. هذا هو ازدواج التخزين الذي يجب إنهاؤه؛ وجود جدول علائقي وحده لا يعني أن الواجهة تستخدمه.

### الاعتماديات الحرجة
- لا يمكن إتمام الاستلام الذري قبل توحيد تمثيل طلب الشراء والبنود والمخزون والإيصال.
- لا يمكن ضمان أحداث Finance/Today قبل إنشاء Outbox دائم داخل معاملة العملية الأصلية.
- لا يمكن فرض صلاحيات العقار/الغرفة بأمان عبر إخفاء عناصر الواجهة فقط؛ يجب أن تتحقق بها RPC/RLS خادميًا.
- لا يمكن اعتماد التذكيرات الخلفية قبل تحديد وقت التنفيذ والمنطقة الزمنية وسياسة تكرار التذكير والتعامل مع التأخير.

## 3. نطاق التنفيذ المقترح بالترتيب

### المرحلة A — توحيد البيانات (أولوية حرجة)
- إنشاء/تعديل repository نطاقي لعمليات Home بدل حفظ aggregate كامل.
- توفير عمليات CRUD/commands ذرية للعقارات والغرف والمخزون والمهام والإنجازات والصيانة ومقدمي الخدمات وطلبات الشراء والبنود والفواتير.
- إضافة optimistic concurrency/نسخة متوقعة أو تحديث على مستوى السجل لتجنب lost updates.
- منع fallback إلى `workspace_data` كمسار كتابة لبيانات Home الحية، وإبقاء Demo منفصلًا.
- إعداد تقرير migration dry-run دون حذف بيانات أو إسقاط جداول.

**بوابة القبول:** كل شاشة تستخدم المصدر العلائقي نفسه؛ لا يوجد dual-write؛ ويظل التعديل المتزامن لسجلين مختلفين محفوظًا دون استبدال snapshot كامل.

### المرحلة B — الاستلام الذري والمخزون
- إنشاء كيان `home_purchase_receipts` وبنود إيصال أو نموذج واضح لتاريخ الدفعات.
- تنفيذ RPC للاستلام تستقبل request id، البنود والكميات، وidempotency key ثابتًا من العميل.
- تقفل الطلب والبنود وصنف المخزون أو تستخدم تحديثات شرطية آمنة.
- في معاملة واحدة: التحقق من المتبقي، إدراج الإيصال، تحديث الكمية المستلمة وحالة الطلب، إنشاء حركة المخزون، تحديث رصيد المخزون، وإضافة أحداث Outbox.
- إعادة الطلب بنفس المفتاح تعيد نتيجة العملية السابقة بدل تكرار الأثر؛ إعادة استخدام المفتاح بحمولة مختلفة تُرفض.

**بوابة القبول:** استلامان متزامنان لا يتجاوزان الكمية المطلوبة؛ إعادة المحاولة لا تضيف رصيدًا/إيصالًا/حدثًا ثانيًا؛ وفشل أي خطوة يلغي المعاملة كلها.

### المرحلة C — Outbox وعمليات التكامل
- إنشاء `home_outbox_events` أو جدول outbox عام مناسب للمنصة مع `event_id`, `workspace_id`, `event_type`, `payload`, `idempotency_key`, `status`, `attempt_count`, `next_attempt_at`, `delivered_at`, `last_error`.
- إدراج الأحداث في نفس معاملة الحدث الأصلي.
- عامل خلفي/Edge Function أو consumer موثوق يسحب الأحداث باستخدام claim/locking، ويسلّمها إلى Finance/Today، ويعيد المحاولة مع backoff، وينقل الأحداث المستنفدة إلى dead-letter.
- Finance يظل «اقتراحًا للمراجعة» ولا يتحول إلى مصروف تلقائيًا.
- منع تكرار الاستهلاك في المستهلك أيضًا بقيد idempotency.

**بوابة القبول:** إغلاق المتصفح لا يفقد الحدث؛ فشل المستهلك يؤدي إلى retry؛ ولا يتكرر الاقتراح المالي أو إنجاز Today عند إعادة التسليم.

### المرحلة D — أعضاء المنزل والصلاحيات
- تعريف عضوية Home على مستوى workspace مع حالة ودور، ثم نطاقات property/room عند الحاجة.
- تحديد الأدوار المسموح بها (مثلاً owner/admin/editor/viewer) بجدول صلاحيات واضح بدل الاعتماد على UI فقط.
- التحقق الخادمي من كل قراءة/كتابة وRPC، واختبارات عزل بين مساحتين وعقارين وغرفتين.
- تحديد سلوك تعيين المهام لعضو تمت إزالته أو فقد صلاحية العقار.

**بوابة القبول:** لا يستطيع عضو view تعديل البيانات؛ ولا يستطيع عضو العقار A قراءة/تعديل العقار B أو غرفة غير مخول لها؛ ويظل المالك قادرًا على إدارة العضوية.

### المرحلة E — التذكيرات الخلفية
- تخزين تذكيرات/مواعيد تنفيذ قابلة للجدولة بدل الاعتماد على `setInterval` داخل الواجهة.
- تحديد المنطقة الزمنية من إعدادات Home، والتعامل مع التوقيت الصيفي وتغيير موعد المهمة وإيقافها/أرشفتها.
- جدولة العامل الخلفي (Supabase Cron/Edge Function أو بنية معتمدة في المشروع) مع سجل محاولات وتسليم.
- تصميم إشعار داخل التطبيق أولًا؛ وPush يحتاج إعداد اشتراك جهاز/متصفح وإدارة إلغاء الاشتراك، ولا يُفترض وجوده قبل اكتمال هذه القطع.

**بوابة القبول:** يصل التذكير دون فتح التطبيق؛ ولا يتكرر بعد إعادة المحاولة؛ والتذكيرات القديمة تُلغى/تُعاد جدولتها عند تغيير المهمة.

### المرحلة F — الاختبارات وقبول الإصدار
- Unit/domain tests للحالات والـ recurrence وحساب المتبقي.
- PostgreSQL isolated migration tests وRLS لكل دور.
- Integration tests لRPC الذرية والـ outbox.
- اختبار تنافس حقيقي أو اختبار متزامن على قاعدة معزولة.
- Browser E2E: إنشاء طلب متعدد البنود → استلام جزئي → إعادة تحميل → استلام الباقي → التحقق من الرصيد والحركات والإيصالات والأحداث.
- اختبار Finance review flow وعدم التسجيل المالي التلقائي.
- اختبار تعدد الجلسات، قطع الاتصال، retry، ومصالحة البيانات.
- تشغيل `npm test`, `npm run lint`, `npm run build` على آخر commit.
- بعد ذلك فقط: تشغيل migrations في مشروع Supabase معزول، مراجعة المخرجات والتقرير، وعدم التفكير في الإنتاج قبل موافقة صريحة منفصلة.
