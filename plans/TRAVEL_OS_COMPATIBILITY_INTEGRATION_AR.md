# استراتيجية التكامل التوافقي لـTravel OS

## القرار
لا نعيد تصميم Core، ولا ننقل ملفات Knowledge، ولا نغيّر عقود البيانات المشتركة. نضيف تكاملات اختيارية خلف adapters صغيرة داخل Travel، وتبقى الميزة متاحة بالقدرات الموجودة عند غياب الخدمة.

## حدود الملكية
- Travel يملك سجلات الرحلات والمحطات والبرنامج والحجوزات والمستندات الوصفية والذكريات.
- الملفات الفعلية تظل في مالكها الحالي. Travel لا ينسخ ملفات Knowledge ولا يقرأها عبر صلاحيات Knowledge.
- Finance يملك الحركات الفعلية؛ Travel يحتفظ بمعرف مرجعي فقط.
- Calendar/Today يملك الأحداث العامة؛ Travel يرسل مرجع مصدر ثابتًا فقط عندما يتوفر عقد تكامل.
- Notifications يملك التسليم وسجل الإشعارات؛ Travel يوفّر تعريف التذكير ومرجعه، ولا ينشئ قناة إشعار ثانية.

## Core Files: مسار توافق دون نقل بيانات
1. لا نستخدم bucket `knowledge-attachments` لملفات Travel؛ سياسات هذا المخزن مرتبطة بصلاحيات Knowledge، وإعادة استخدامه قد تمنح/تحجب وصولًا بصورة غير صحيحة.
2. تبقى حقول `storageNote` و`mediaPath` الحالية صالحة للقراءة والتصدير المتوافق، لكن لا تُعرض كأنها ملف مرفوع أو رابط آمن.
3. يضاف adapter اختياري يكتشف خدمة ملفات مشتركة إن وُجدت، ويعرض حالة واضحة عند غيابها؛ لا يرفع أو يحذف من Storage مباشرة ولا ينشئ bucket جديدًا ضمن هذه المرحلة.
4. واجهة المستندات والذكريات تميّز بين «مرجع ملف قديم» و«ملف قابل للفتح عبر خدمة معتمدة». لا حذف تلقائيًا للملفات عند حذف سجل Travel.
5. لا تُصنّف ميزة الرفع/العرض/الحذف مكتملة حتى يثبت وجود API مشترك واختبار وصول بحسابين مختلفين.

## Notifications
- توليد معرف مصدر ثابت: `travel:<workspaceId>:<kind>:<recordId>:<dueAt>`.
- لا يُنشأ تذكير مكرر عند إعادة الحفظ؛ upsert/idempotency يجب أن يكون مسؤولية خدمة الإشعارات المشتركة.
- إذا لم توجد واجهة خدمة معتمدة، تبقى تنبيهات Travel داخل لوحة القسم فقط ولا ندّعي إرسال Push/إشعار عام.
- إلغاء الحجز أو تعديل انتهاء الوثيقة يحدّث/يلغي التذكير المرجعي ولا يمس إشعارات الأنظمة الأخرى.

## Offline & Sync
- نعتمد على Core record store والطابور الموجودين بدل إنشاء طابور Travel آخر.
- عند انقطاع الشبكة، نوضح حالة الحفظ المحلي/بانتظار المزامنة؛ لا نعرض نجاحًا خادميًا غير مؤكد.
- عند التعارض، لا نكتب فوق نسخة الخادم تلقائيًا؛ نحافظ على سلوك Core الحالي الذي يحتفظ بالتعديل المتعارض للمراجعة.
- تُختبر سيناريوهات: تعديل offline ثم reconnect، إعادة تحميل مع queue معلّق، تعديلان على سجل واحد، حذف متزامن، وفشل الشبكة أثناء replay.

## Calendar / Today
- لا ننشئ حدثًا موازيًا داخل Calendar مباشرة من كل render أو حفظ.
- مرجع الحدث المقترح ثابت: `sourceSystem='travel'` و`sourceRecordId=<itineraryId>`.
- إنشاء/تحديث/حذف الحدث عبر عقد idempotent فقط؛ إذا لم يوجد العقد، يبقى البرنامج داخل Travel دون نسخ تلقائي إلى التقويم.
- نستخدم المنطقة الزمنية المحفوظة للمحطة عند توفرها، ولا نخمن تحويل التوقيت.

## علاقات الأنظمة الأخرى
- Relationships: معرف الشخص فقط؛ لا نسخ ملف الشخص إلى Travel.
- Knowledge: روابط معرفات المعرفة ومصادرها فقط؛ لا نسخ المحتوى.
- Shopping: مرجع wishlist/product فقط، ولا إنشاء مشتريات من Travel.
- Inventory: مرجع أصل/غرض فقط، ولا تعديل المخزون تلقائيًا.
- Finance: مراجع القراءة فقط كما هو قائم؛ لا إنشاء أو تعديل حركات من Travel.

## بوابة القبول
- غياب خدمة اختيارية لا يكسر فتح Travel أو تعديل الرحلات.
- صلاحيات النظام المصدر هي الحاكمة؛ لا توسّع صلاحيات عن طريق adapter.
- لا بيانات أو ملفات وهمية في مساحة العمل الحقيقية.
- اختبارات الدومين الآلية لا تُعد بديلًا لاختبار RLS/Storage أو الاختبار اليدوي.
- لا دمج أو نشر إنتاجي ضمن هذه الخطة.
