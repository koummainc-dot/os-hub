# Home OS — المرحلة التشغيلية الثانية (حالة التنفيذ)

## ما أصبح موصولًا في واجهة Home OS
- المهام المنزلية: إنشاء وتعديل، تحديد العقار والغرفة، أولوية وموعد ومدة تقديرية، تكرار يومي/أسبوعي/شهري/سنوي/كل N أيام، تسجيل الإنجاز أو التخطي، إيقاف مؤقت/استئناف/أرشفة.
- الصيانة: تسجيل العطل، ربط العقار والغرفة وعنصر المخزون ومقدم الخدمة، الحالة والأولوية والتكلفة وموعد الصيانة القادمة.
- المشتريات: طلبات شراء وبنود متعددة، كمية وسعر تقديري، اعتماد الطلب ثم تسجيله لدى المورد ثم الإلغاء أو الاستلام، واستلام جزئي لكل بند مع تحديث حركة المخزون. مفاتيح idempotency منفصلة حسب نقطة الاستلام تمنع تكرار الحركة عند إعادة المحاولة.
- الفواتير: مبالغ وتصنيفات واستحقاقات يومية/أسبوعية/شهرية/ربع سنوية/سنوية أو مرة واحدة، مع حساب تاريخ الاستحقاق التالي بطريقة تراعي نهاية الشهر والسنة الكبيسة.
- مقدمو الخدمات: الاسم والتصنيف والهاتف والبريد والتقييم والملاحظات.
- التقارير: أعداد المهام المكتملة والنشطة، الصيانة المفتوحة، طلبات الشراء، الفواتير المتأخرة، وإجماليات تكاليف مسجلة.
- عمليات المهام والإنجازات والصيانة ومقدمي الخدمات والمشتريات والفواتير تُقرأ وتُحفظ علائقيًا عند وجود بيانات؛ الـ snapshot القديم مرآة توافقية مؤقتة، والقراءة تفضّل الجداول العلائقية.
- أُضيفت `home_operations_load_v2/save_v2` مع optimistic concurrency وقفل لكل مساحة عمل؛ الحفظ بنسخة قديمة يرفض برسالة تعارض بدل الكتابة فوق تحديث أحدث.
- الاستلام الجزئي والنهائي يُسجل عبر RPC ذرية تشمل إيصالًا وبنوده وحركة المخزون وتحديث حالة الطلب وAudit وOutbox. إعادة المحاولة بنفس المفتاح لا تضاعف الرصيد حتى بعد اكتمال الطلب.
- حركات المخزون العامة تستخدم RPC ذرية، وتمنع الصرف فوق المتاح، كما يمنع Trigger تغيير رصيد عنصر موجود مباشرة دون حركة موثقة. واجهة تعديل العنصر تعرض الرصيد الحالي للقراءة فقط.
- الفواتير والاستحقاقات والمدفوعات لها جداول علائقية، وتعرض الواجهة سجل المدفوعات السابقة. أحداث Finance/Today تُحفظ في Outbox دائم داخل معاملة الحفظ؛ لا يوجد dispatcher خادمي يضمن تسليمها بين الأجهزة حتى الآن.
- Finance OS يقرأ اقتراحات Home المعلقة من `home_finance_outbox_load`؛ استلام المشتريات ينتج حدثًا منفصلًا لكل بند بكمية وتكلفة ومفتاح مصدر ثابت، وتُفلتر الأحداث التي لها معاملة مالية مسجلة بالفعل.
- بعد حفظ المعاملة في Finance، يستدعي التطبيق `home_finance_outbox_ack` لإخفاء الاقتراح المستهلك من قائمة المعلّق؛ صفحة Today تقرأ إنجازات المهام من `home_today_outbox_load`.
- تقرير `home_operations_reconciliation_report` يقارن أعداد السجلات وبصمات المعرّفات قبل إزالة fallback، لكنه لا يغني عن مقارنة الحقول والعلاقات وتشغيله على بيانات معزولة فعلية.
- العقارات/الغرف/المخزون لها الآن `home_load_snapshot_v2/save_v2` مع رفض الكتابة بنسخة قديمة، كما يمنع trigger تعديل الرصيد مباشرة دون حركة دفترية.

## حدود يجب ألا يتم الادعاء بتجاوزها
- الميزة لا تزال داخل PR Draft، ولم تُدمج.
- Migration لم تُطبق على الإنتاج؛ لا تعمل شاشات العمليات للمستخدم الحقيقي قبل تطبيق migrations بالترتيب والتحقق من الصلاحيات.
- نجح Home OS PostgreSQL smoke على head قريب بعد تطبيق migrations حتى `20261031220000_home_os_inventory_ledger_guard.sql`، بما يشمل التزامن، الاستلام، سجل الفواتير، وحظر تغيير الرصيد المباشر. ما زالت CI وVerify app على أحدث head قيد التشغيل؛ لا يُعلن قبول التطبيق النهائي قبل نجاحهما. Vercel Preview قد يظل متأثرًا بحد بناء الحساب، وهذا منفصل عن اختبارات CI.
- عند دفع فاتورة، أو تسجيل استلام مشتريات بتكلفة معروفة، أو إكمال صيانة بتكلفة موجبة، يُرسل Home حدثًا إلى Finance لمراجعة المستخدم واختيار الحساب والتصنيف قبل تسجيل المصروف؛ مفاتيح idempotency تمنع تكرار المعاملة لكل دفعة/استلام/دورة إكمال. النقل الحالي عبر localStorage/أحداث المتصفح فقط، وليس ناقل أحداث خادميًا دائمًا أو مزامنة موثوقة بين الأجهزة.
- أُضيفت تذكيرات للمهام أثناء فتح التطبيق، مع خيار طلب إذن إشعارات المتصفح. لا توجد إشعارات push أو جدولة خلفية عندما يكون التطبيق مغلقًا، ويجب اختبار التوقيت والصلاحيات في المتصفح.
- أُضيف تعيين المهمة إلى مالك مساحة العمل أو عضو حالي والتحقق من أن المسؤول عضو فعلي. ما زالت إدارة أعضاء المنزل نفسها والصلاحيات التفصيلية على مستوى العقار/الغرفة غير موجودة. لا توجد إشعارات push أو جدولة خلفية عند إغلاق التطبيق.
- نجح اختبار PostgreSQL المعزول الحالي، لكن ما زالت اختبارات القبول المرئية E2E، واختبار مستخدمين/جلستين حقيقيين، وصلاحيات العقار/الغرفة، وOutbox dispatcher، وتذكيرات الخلفية، ومصالحة البيانات التاريخية مطلوبة قبل اعتماد القسم.

## حدود التكامل
- Home OS هو مصدر الحقيقة للمهام المنزلية والمشتريات والصيانة والفواتير المنزلية.
- مخزون المنزل محفوظ في بيانات Home OS، ويستقبل حركة receive ذات مفتاح idempotency ثابت عند استلام طلب الشراء.
- Finance لا يملك نسخة مكررة من فاتورة المنزل حتى يتم إنشاء ربط صريح بمعاملة مالية.
- عند إكمال مهمة منزلية، يُرسل Home حدثًا يظهر في Today ضمن «إنجازات المنزل»، دون نقل ملكية المهمة إلى Today. هذا التكامل الحالي محلي عبر المتصفح؛ يلزم event bus خادمي حتى يعمل بين الأجهزة والجلسات المختلفة.

## بوابة القبول
1. تطبيق migrations في مشروع Supabase معزول فقط، لا الإنتاج.
2. تشغيل npm test وnpm run lint وnpm run build على آخر head.
3. اختبار مستخدم view لا يستطيع الحفظ، ومستخدم edit يستطيع الحفظ داخل workspace المصرح فقط.
4. اختبار إعادة محاولة استلام طلب شراء لا يكرر زيادة المخزون.
5. اختبار تكرار المهام عند نهاية الشهر والسنة الكبيسة، وتواريخ الفواتير المتكررة.
6. اختبار reload/session جديدة للتأكد من استمرار البيانات من Supabase وليس localStorage.
7. اختبار الشاشات في المتصفح قبل رفع Draft/اعتماد المرحلة.

## مراجعة الفيتشرز بعد آخر دفعة تعديلات

### تم تنفيذه في الكود (بانتظار تحقق آخر head)
- الاستلام الجزئي للمشتريات: إدخال كمية مستلمة الآن لكل بند، إبقاء المتبقي، وتحديث حالة الطلب إلى `partially_received` أو `received`.
- منع تكرار حركة المخزون لكل دفعة استلام باستخدام مفتاح مشتق من الطلب والبند والكمية المستلمة سابقًا؛ إعادة المحاولة قبل تحديث سجل الطلب تستخدم المفتاح نفسه.
- دورة حالة المشتريات: اعتماد `needed → approved`، تسجيل الطلب لدى المورد `approved → ordered`، ثم استلام جزئي/كامل أو إلغاء وفق الحالة.
- حساب مواعيد الفواتير الدورية مع ضبط نهاية الشهر والسنة الكبيسة، والتحقق من صحة التاريخ الفعلي لا مجرد شكل YYYY-MM-DD.
- حدث دفع الفاتورة إلى Finance مع مراجعة بشرية قبل إنشاء المعاملة، ومفتاح idempotency في طلب تسجيل الحركة.
- حدث إنجاز المهمة إلى Today لعرضه ضمن إنجازات المنزل.
- اختبارات domain جديدة لتواريخ الفواتير وحدود نهاية الشهر والسنة الكبيسة وحالات الاستلام.

### ما زال يمنع الاعتماد النهائي
1. **مصدر حقيقة العمليات:** واجهة العمليات تحفظ JSON snapshot، بينما migration السابقة تنشئ جداول علائقية للمهام والصيانة والمشتريات. الجداول العلائقية ليست مصدر الحقيقة الفعلي حتى الآن؛ يجب اختيار مسار واحد ثم ترحيل البيانات واختبار التوافق.
2. **المزامنة بين الأجهزة:** أحداث Finance وToday محلية best-effort؛ يلزم تخزين/نشر server-side أو outbox متين حتى لا تضيع الأحداث أو تتكرر بين الأجهزة.
3. **إدارة الأعضاء والصلاحيات:** تعيين المهمة إلى مالك/عضو مساحة العمل موجود؛ ما زال ينقص إدارة أعضاء منزل مستقلة وصلاحيات granular على مستوى العقار/الغرفة.
4. **التذكيرات:** لا توجد جدولة خلفية أو push عند إغلاق التطبيق، ولا اختبار فعلي عبر المتصفحات/الأجهزة.
5. **التحقق الحالي:** آخر CI أخضر معروف يخص head أقدم؛ لم يتم تأكيد npm test/lint/build على آخر head بعد تغييرات الاستلام الجزئي والتكاملات.
6. **اختبارات القبول:** اختبار PostgreSQL المعزول للمigrations وRLS ومستوى view/edit ومنع تكرار حركة المخزون اجتاز. ما زال ينقص اختبار متصفح فعلي، اختبار RLS شامل على مشروع Supabase معزول، واختبار تزامن/تعارض حفظ snapshot.
7. **تكامل التكاليف:** دفع الفاتورة فقط يرسل اقتراحًا إلى Finance؛ تكاليف الصيانة والمشتريات لا تنشئ/تقترح حركات مالية بنفس مسار المراجعة حتى الآن.
8. **تطبيق migrations:** لا تُطبق على الإنتاج قبل اختبارها في Supabase معزول وحسم ازدواج snapshot/relational tables.

### آخر تحديث تكاملي
- أضيفت أحداث تكاليف استلام المشتريات (تُحسب من الكمية المستلمة × تكلفة الوحدة المعروفة فقط).
- أضيفت أحداث تكلفة الصيانة عند الانتقال إلى الحالة «مكتملة» لأول مرة/في دورة إكمال جديدة، بشرط وجود تكلفة موجبة.
- تستقبل Finance أحداث الفواتير والمشتريات والصيانة في قائمة مراجعة واحدة؛ لا يتم تسجيل المصروف إلا بعد تأكيد المستخدم، ويستخدم idempotency key عند الحفظ.

## قرار معماري ملزم — 2026-10-31

تم حسم السؤال المعماري في [ADR-HOME-001 — مصدر الحقيقة لبيانات Home OS](ADR_HOME_001_SOURCE_OF_TRUTH_AR.md):

**مصدر الحقيقة النهائي للعمليات المنزلية هو الجداول العلائقية في PostgreSQL/Supabase.** لا يجوز أن تستمر الواجهة في كتابة JSON snapshot للمهام والصيانة والمشتريات والفواتير بالتوازي مع الجداول العلائقية. يقتصر JSONB على بيانات وصفية/مرنة غير معاملية، ويقتصر localStorage على cache أو تفضيلات قابلة لإعادة البناء.

### أثر القرار على التنفيذ

1. قبل أي migration جديدة: جرد المخطط الموجود وملفات migrations وواجهات repository، ثم إعادة استخدام أي جداول/كيانات قائمة وتجنب تكرار العقارات والغرف والمخزون.
2. نقل عمليات القراءة والكتابة إلى repository علائقي واحد؛ لا dual-write ولا استبدال snapshot كامل عند الحفظ.
3. تنفيذ الاستلام الجزئي وتحديث المتبقي وحركة المخزون وإضافة حدث outbox داخل معاملة ذرية واحدة، مع مفتاح idempotency ثابت وفريد لكل دفعة استلام.
4. إنشاء outbox خادمي دائم لأحداث Finance وToday. تظل المعاملة المالية النهائية بيد المستخدم بعد مراجعة الاقتراح.
5. تنفيذ ترحيل legacy عبر dry-run وتقرير فروقات ومصالحة أعداد/علاقات قبل تعطيل snapshot، دون حذف أو إسقاط بيانات في هذه الخطوة.
6. تطبيق migrations واختبارات RLS على مشروع معزول فقط. المشروع الحالي لم تُطبق عليه أي migration خاصة بـ Home في هذه المهمة؛ لم تُجر أي كتابة إلى قاعدة البيانات.
