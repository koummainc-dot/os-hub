# Projects Outputs — Direct Upload Safety Plan\n\nStatus: design reviewed; implementation intentionally deferred until access contracts are verified.\n\n## Free-path decision\n\nUse the existing Supabase project os-hub and Supabase Storage; do not create a paid branch or separate paid environment.\n\nSupabase's current Storage documentation supports browser uploads through supabase-js and RLS policies on storage.objects. The Free plan currently caps the global maximum file size at 50 MB and provides 10 GB of Storage bandwidth/egress allowance. Standard uploads are recommended for small files; resumable/TUS uploads are the safer path when files exceed about 6 MB or network reliability matters.\n\n## Proposed Outputs contract\n\n- One private Files bucket dedicated to Projects outputs.\n- Object path is workspace-scoped, for example: workspace/{workspaceId}/project/{projectId}/output/{outputId}/{opaqueFileId}-{safeName}\n- Never trust a client-supplied workspace/user path for authorization.\n- The application record remains the source of truth for the Output; Storage holds the binary.\n- Output files[] stores metadata only: object path, filename, MIME type, byte size, uploaded timestamp, and optional checksum.\n- No base64/data-URL persistence.\n- No public bucket.\n- No service_role key in the browser.\n- Prefer non-overwriting uploads with unique object paths; this avoids unnecessary SELECT/UPDATE policy requirements and CDN propagation issues.\n- If deletion is implemented, the Storage object and Output metadata must be reconciled so a failed object deletion cannot silently claim the file is gone.\n\n## Required RLS design before migration\n\nStorage policies must reuse the application's real workspace membership/role contract rather than inventing a second authorization model.\n\nMinimum operations:\n- INSERT for authorized Project output writers.\n- SELECT only for users authorized to read the same Project/workspace output.\n- DELETE only for users authorized to remove the output attachment.\n- UPDATE only if replacement/upsert is explicitly supported.\n\nThe policy must enforce both workspace membership and the project/output scope encoded in the object path. TO authenticated alone is insufficient.\n\n## Size/type policy\n\nStart conservatively:\n- default per-file limit: 50 MB maximum because Free cannot exceed that global limit;\n- smaller application limit for normal Outputs (for example 10 MB) can be enforced client-side and server-side where possible;\n- allow common document/image types first;\n- reject executable/script formats;\n- preserve the original filename only as display metadata; use an opaque object ID in the Storage path.\n\n## Migration gate\n\nDo not create the bucket or Storage policies yet.\n\nBefore migration:\n1. inspect the actual Projects workspace membership and permission helper/RLS contracts;\n2. confirm how Projects Output rows are persisted in the current backend;\n3. add/keep contract tests for upload metadata, no base64 persistence, object-path scoping, non-public bucket, and no service-role usage;\n4. generate a migration only after the access model is confirmed;\n5. run Supabase advisors and disposable RLS/storage smoke tests;\n6. only then consider applying the migration to the intended target after explicit release review.\n\n## Current repository state\n\nThe Projects UI already supports Output files[] metadata and displays attached-file metadata, but it does not perform a real Storage upload. This is intentional until the authorization contract is verified.
