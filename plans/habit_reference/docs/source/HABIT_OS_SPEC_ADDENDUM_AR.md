# ملحق مواصفات Habit OS — الجدولة ودورة حياة البيانات والميزات

**الغرض:** استكمال ملف `01_HABIT_OS_INDEPENDENT_BUILD_SPEC.md` (الإصدار 2.0) بقرارات تنفيذية واضحة للنقاط التي تُركت مفتوحة، وبميزات مهمة شائعة في تطبيقات تتبّع العادات.

**قاعدة التطبيق:** عند التعارض، يُطبّق هذا الملحق على النقاط التي يحددها صراحةً، وتظل بقية مواصفات الملف الأصلي سارية. العبارات **يجب** و**لا يجوز** متطلبات تنفيذية؛ و**يفضّل** توصية.

---

## 16. جدولة العادة ومدتها

### 16.1 إنشاء جدول مرن

يجب أن تسمح شاشة إنشاء/تعديل العادة بتحديد **متى تتكرر**، و**تاريخ بدايتها**، وهل لها تاريخ نهاية. لا تُخزّن الجدولة كنص حر؛ تحفظ كقاعدة قابلة للحساب.

أنماط الجدولة المطلوبة:

| النمط | أمثلة |
|---|---|
| يوميًا | كل يوم، أو كل يومين/كل N أيام |
| أيام محددة من الأسبوع | الاثنين والأربعاء والجمعة؛ أو أيام العمل من الاثنين إلى الجمعة |
| عدد مرات في الأسبوع | 3 مرات بين بداية الأسبوع ونهايته، من دون اشتراط أيام بعينها |
| أسبوعيًا | كل أسبوع في يوم محدد، أو كل أسبوعين |
| شهريًا | يوم محدد من الشهر؛ أو يوم أسبوعي محدد مثل أول اثنين |
| عدد مرات في الشهر | 8 مرات خلال الشهر مثلًا |
| مخصص | تكرار كل N أيام/أسابيع/أشهر، مع أيام أو حدود اختيارية عند الحاجة |

**الاختيار الافتراضي المقترح:** يومي، أو أيام محددة، أو عدد مرات أسبوعيًا. الأنماط الشهرية والتكرار كل N فترة جزء من المحرك الأساسي، حتى لو كانت أقل ظهورًا في شاشة البداية.

> «ثلاث مرات في الأسبوع» ليست الشيء نفسه مثل «الاثنين والأربعاء والجمعة»: الأولى هدف عددي داخل أسبوع، والثانية مواعيد محددة.

### 16.2 حقول الجدولة المقترحة

أضف إلى العادة أو إلى كيان جدول مرتبط بها:

- `tracking_type`: `check` أو `quantity` أو `duration` أو `avoidance`.
- `schedule_type`: `daily` أو `weekdays` أو `times_per_period` أو `interval` أو `monthly` أو `custom`.
- `schedule_rule`: كائن منظم يصف الأيام، والفاصل، والعدد المطلوب، وبداية الأسبوع، وقاعدة اليوم الشهري.
- `start_date`: تاريخ بداية العادة، مطلوب.
- `end_date`: تاريخ النهاية، اختياري؛ `null` يعني **مستمرة بلا نهاية محددة**. النهاية شاملة لليوم المحدد.
- `timezone`: المنطقة الزمنية المعتمدة للمستخدم عند احتساب حدود اليوم/الأسبوع/الشهر.
- `reminder_rules`: صفر أو أكثر من تذكيرات العادة، ويُشرح في قسم الإشعارات.

مثال توضيحي لعادة ثلاث مرات أسبوعيًا:

```json
{
  "schedule_type": "times_per_period",
  "schedule_rule": {
    "period": "week",
    "target_count": 3,
    "week_starts_on": "monday"
  },
  "start_date": "2026-10-01",
  "end_date": null
}
```

ومثال لعادات أيام محددة:

```json
{
  "schedule_type": "weekdays",
  "schedule_rule": { "days": ["monday", "wednesday", "friday"] },
  "start_date": "2026-10-01",
  "end_date": null
}
```

يجب أن تكون قواعد الشهر صريحة عند تواريخ مثل اليوم 29 أو 30 أو 31: اختر سياسة ثابتة، ويوصى بأن **يتخطى** النظام الشهر الذي لا يحتوي اليوم المحدد، مع إتاحة اختيار «آخر يوم من الشهر» كقاعدة مستقلة.

### 16.3 تعريف موعد الاستحقاق والسلاسل

1. الموعد غير المجدول **محايد**: لا يُنشأ له سجل فائت، ولا يقطع السلسلة، ولا يدخل في مقام نسبة الالتزام.
2. العادة ذات الأيام المحددة تُقاس بالسلسلة عبر **المواعيد المجدولة المتتالية**، وليس عبر كل أيام التقويم. الأيام بين المواعيد لا تكسر السلسلة.
3. العادة ذات هدف `N` مرات في الأسبوع/الشهر تُقاس بسلسلة **فترات**: تستمر السلسلة إذا تحقق العدد المطلوب في كل فترة مكتملة متتالية. لا تُحكم الفترة الحالية قبل انتهائها.
4. عادة `daily` تُقيّم لكل يوم وفق المنطقة الزمنية للمستخدم. عادة «كل يومين» تُقيّم في مواعيدها المتولدة من تاريخ البداية.
5. لا تُعتبر الفترة الجارية فائتة قبل نهاية آخر يوم فيها. بعد نهاية الفترة، غياب العدد المطلوب يعامل كفشل في تلك الفترة لأغراض السلسلة والإحصاء، **من دون إنشاء سجل يومي تلقائي**؛ وهذا يحافظ على شرط المواصفة الأصلية.
6. يجب فصل المؤشرات: `current_streak`، و`best_streak`، و`compliance_ratio`، و`completed_occurrences`. يوضّح التطبيق للمستخدم هل السلسلة محسوبة بأيام أم بمواعيد أم بفترات أسبوعية/شهرية.
7. تُحتسب نسب الالتزام على المواعيد/الفترات المستحقة فقط؛ لا تدخل الأيام المستقبلية أو غير المجدولة في الحساب.

### 16.4 الإجازة والتخطي والتوقف

يجب التفريق بين الحالات التالية:

- **Vacation / Excused:** استثناء لموعد مجدول بعينه؛ لا يُحسب إنجازًا ولا إخفاقًا، ولا يقطع السلسلة. يسجل المستخدم سببًا اختياريًا. يمنع إساءة الاستخدام بوضع إعداد واضح: إجازة لموعد واحد أو نطاق تواريخ.
- **Skip:** تخطٍ يدوي لموعد مجدول. افتراضيًا هو استثناء محايد لا إنجاز ولا إخفاق، ويظهر منفصلًا في الإحصاءات؛ لا يُخلط مع `Done`.
- **Missed:** إخفاق لموعد مستحق لم يُنجز، أو وُسم فائتًا يدويًا. يقطع السلسلة.
- **Paused:** إيقاف العادة من تاريخ إلى تاريخ/حتى الاستئناف. فترة الإيقاف خارج المواعيد المستحقة، فلا تقطع السلسلة. لا تُحذف سجلات ما قبل الإيقاف.
- **Archived:** إخفاء العادة من الاستخدام النشط والتركيز، مع بقاء التاريخ قابلًا للعرض.

يظل الحقل الأصلي `Vacation` متوافقًا؛ ويُضاف `Skipped` أو `Excused` إذا احتاج التنفيذ تمييز التخطي عن الإجازة. لا يُعدّل سجل لمجرد عدم وجود إنجاز. في حال تعدد الاستثناءات يجب عرضها في سجل المواعيد دون تضخيم نسبة النجاح.

### 16.5 الكمية والإنجاز الجزئي

للعادات من نوع `quantity` أو `duration`:

- `goal` هو الهدف؛ ويجب أن يكون أكبر من صفر.
- `minimum` هو الحد الأدنى المقبول، ويجب أن يكون بين صفر والهدف. يوصى بأن يساوي صفرًا افتراضيًا إذا لم يحدده المستخدم.
- إذا كان `actual >= goal` فالحالة `Done`.
- إذا كان `minimum > 0` و`minimum <= actual < goal` فالحالة `Partial`.
- إذا كان `actual < minimum` فالحالة `Missed` عند إغلاق الموعد/الفترة، أو تُترك غير محسومة حتى نهاية الفترة.
- عند `minimum = 0` لا تجعل قيمة صفر إنجازًا؛ يلزم `actual > 0` على الأقل لاحتساب تقدم جزئي، وإلا تكون فائتة عند الإغلاق.
- `check` (نعم/لا) لا يحتاج كمية. `avoidance` يُقاس بعدد الأيام النظيفة والأحداث، ولا يُعامل كهدف إنجاز اعتيادي.
- تظل نسبة الإنجاز محدودة بـ 1.0 كما في المواصفة الأصلية، مع إمكان عرض الكمية الفعلية منفصلة عند تجاوز الهدف.

### 16.6 تغييرات الجدول والهدف مع التاريخ

لا يجوز لتعديل جدول اليوم أن يعيد تفسير الماضي بصمت. اعتمد نسخة مؤرخة من إعدادات العادة:

- كل تغيير للجدول أو الهدف أو الحد الأدنى ينشئ **نسخة تسري من تاريخ محدد** (`effective_from`)، والافتراضي هو اليوم أو تاريخ يختاره المستخدم.
- تحتفظ سجلات العادة وقت إنشائها بقيم الهدف/الوحدة/قاعدة الجدول التي كانت سارية، أو ترتبط بنسخة الإعداد السارية؛ كي لا يتغير معنى الإنجاز التاريخي عند تعديل الهدف لاحقًا.
- عند تغيير الجدول مستقبلًا، أعد حساب المواعيد والمؤشرات من تاريخ السريان فصاعدًا، مع الحفاظ على نتائج التاريخ السابقة.
- تغيير المنطقة الزمنية لا ينقل السجلات القديمة إلى يوم آخر؛ لكل سجل تاريخ محلي محفوظ، وتُستخدم المنطقة الزمنية السارية لحدود الفترات.

## 17. عمليات الإضافة والتعديل والحذف والأرشفة

يجب أن تدعم كل شاشة قائمة تفاصيل واضحة لإضافة العناصر وتعديلها وأرشفتها أو حذفها بحسب القواعد التالية. الإضافة والتعديل والحذف تكون بواجهة مباشرة، مع رسائل نجاح/خطأ وتأكيد عند العمليات غير القابلة للاسترجاع.

| الكيان | إضافة | تعديل | حذف/أرشفة |
|---|---|---|---|
| Habit | إنشاء عادة جديدة | تعديل الاسم والوصف والجدول والهدف والمستوى والحالة والروابط | **أرشفة افتراضية** تحفظ السجلات. الحذف النهائي لا يُتاح إلا بعد توضيح أثره واختيار مصير السجلات المرتبطة |
| Daily Log | تسجيل سريع من شاشة اليوم، أو إدخال/استدراك تاريخ سابق | تعديل الحالة والكمية والملاحظة والتاريخ؛ يعاد حساب كل المقاييس المتأثرة | حذف/إلغاء السجل مع إعادة الحساب. قبل الحذف يوضح أثره على السلسلة والإنجازات |
| Relapse | تسجيل انتكاسة جديدة | تعديل وقت الانتكاسة والمحفز والخطورة والخطة والنتيجة | حذف/إلغاء حدث الانتكاس يعيد احتساب أيام النظافة والسلسلة النظيفة من كامل التاريخ |
| Journal | إنشاء يومية من تدفق «يومية جديدة» | تعديل جميع الحقول والوسوم والروابط | نقل لسلة محذوفات قابلة للاستعادة، ثم حذف نهائي بطلب المستخدم |
| Book | إضافة كتاب | تعديل البيانات والحالة والتقدم والملاحظات | حذف الكتاب لا يحذف سجل العادات أو القراءة؛ يزيل علاقة الكتاب من السجلات المرتبطة أو يترك لقطة نصية اختيارية |
| Weekly Focus | إنشاء مراجعة/أسبوع جديد | تعديل العادات والتقييم والمراجعة | حذف المراجعة فقط؛ لا يحذف سجلات العادات. منع تكرار أسبوع المستخدم نفسه |
| Achievement | تعريف إنجاز مخصص أو استخدام إنجاز افتراضي | تعديل الاسم والشرط والعتبة؛ لا يسمح بتعديل القيم المشتقة يدويًا | تعطيل/أرشفة الإنجاز. يبقى تاريخ الحصول عليه في السجل ما لم يطلب المستخدم حذفه |

### 17.1 سياسة الحذف المقترحة

- استخدم **الأرشفة** للعادات والإنجازات التي لها تاريخ أو علاقات؛ الأرشفة لا تعني حذف البيانات.
- استخدم سلة محذوفات للبيانات القابلة للاستعادة لمدة افتراضية قابلة للضبط (يوصى بـ 30 يومًا). بعد ذلك لا يتم الحذف النهائي إلا وفق سياسة الاحتفاظ التي يعلنها المنتج.
- الحذف النهائي لعادة لها سجلات يحتاج اختيارًا صريحًا: **إلغاء العملية**، أو **حذف العادة مع سجلاتها المرتبطة**. لا تحذف البيانات التاريخية تلقائيًا دون إظهار نتيجة الاختيار.
- عند حذف كتاب، اجعل `book_id` في السجلات المرتبطة فارغًا بدل حذف السجلات.
- عند حذف/إخفاء يومية، لا تُحذف العادة أو السجلات المرتبطة بها؛ يُزال الرابط فقط.
- نفّذ إعادة حساب المؤشرات والإنجازات بعد أي إضافة أو تعديل أو حذف لسجل مؤثر، واجعل العملية آمنة عند إعادة الطلب (idempotent).
- يجب دعم الاستعادة من سلة المحذوفات قبل الحذف النهائي. وعند الاستعادة، أعد الروابط الممكنة وأعد حساب المؤشرات.
- حذف حساب المستخدم/كل بياناته عملية منفصلة ذات تأكيد صريح، وتلتزم بسياسة الخصوصية والاحتفاظ المعتمدة.

### 17.2 التحقق والتعارض

- امنع السجلات المكررة لنفس المستخدم/العادة/الموعد وفق مفتاح الموعد، أو اعرض خيار تعديل السجل الموجود بدل إنشاء نسخة ثانية.
- امنع تعديل عناصر مستخدم آخر، حتى عند معرفة المعرّف.
- لا تسمح بحذف/تعديل قيمة مشتقة مثل `current_value` أو `is_achieved` يدويًا.
- أظهر ملخصًا قبل التغيير التاريخي: التاريخ المتأثر، والسلسلة/الإحصاءات التي ستُعاد محاسبتها.

## 18. قيم افتراضية موحّدة

القيم التالية اقتراح افتراضي لتجنب الحقول المفتوحة في الوثيقة الأصلية؛ يجب جعلها قابلة للتغيير في الإعدادات حيث يلزم:

| الحقل | القيمة/السلوك الافتراضي |
|---|---|
| حالات العادة | `Active`, `Paused`, `Archived`، مع حالة مشتقة `Ended` عند تجاوز `end_date` |
| حالة الكتاب | `Want to Read`, `Reading`, `On Hold`, `Completed`, `Abandoned` |
| تقييم الكتاب | من 1 إلى 5 نجوم، اختياري |
| تقييم الأسبوع | من 1 إلى 5، اختياري |
| المزاج والطاقة | مقياس 1–5 مع تسميات نصية قابلة للتخصيص، اختياري |
| شدة الانتكاسة | 1–5، اختياري؛ لا تدخل في حساب أيام النظافة ما لم يقرر المستخدم ذلك |
| بداية الأسبوع | الاثنين افتراضيًا، قابلة للتغيير حسب إعدادات المستخدم |
| حد الأهداف الأسبوعية | تحذير فوق 5 عادات تركيز، كما في المواصفة الأصلية؛ لا منع ولا حذف تلقائي |
| منطقة التوقيت | منطقة المستخدم الصريحة؛ لا تعتمد على تخمين الخادم |

يُفضّل توحيد القيم المرجعية عبر إعدادات المستخدم، لا تركها كنصوص مختلفة في كل سجل.

## 19. ميزات شائعة أخرى: ما الموجود وما يُقترح إضافته

راجعت صفحات التطبيقات الرسمية: [Habitify على App Store](https://apps.apple.com/us/app/habitify-habit-tracker/id1111447047)، و[Loop Habit Tracker على Google Play](https://play.google.com/store/apps/details?id=org.isoron.uhabits&hl=en_US)، و[Streaks](https://streaksapp.com/). هذه مقارنة **لأفكار ميزات معلنة** وليست توصية بتقليد تطبيق بعينه.

| الميزة | وضعها في المواصفة الأصلية | اقتراح الملحق |
|---|---|---|
| تكرار مرن يومي/أيام محددة/عدد مرات أسبوعيًا/كل فترة | مذكور بشكل عام دون تعريف | **أساسي** — حسمه في القسم 16 |
| تاريخ بداية ونهاية مفتوحة أو محددة | غير موجود كحقول | **أساسي** — أضف البداية والنهاية الاختيارية |
| إيقاف مؤقت وتخطي/إجازة | يوجد Vacation وPaused في الحالة، لكن معناهما غير مفصل | **أساسي** — فصل الاستثناء عن الإخفاق والإنجاز |
| تذكيرات متعددة حسب العادة والوقت | تذكير يومي/أسبوعي اختياري فقط | **مهم** — تذكير/أكثر لكل عادة، وإعادة جدولة/Snooze، وكتم التذكير بعد الإكمال |
| تسجيل سريع من الإشعار أو أداة الشاشة | Quick Log موجود، لكن لا إشعار تفاعلي أو Widget موصوف | **مهم** — Quick Log من لوحة اليوم؛ Widgets بعد اختيار المنصة |
| تاريخ كامل وتقويم ورسوم | إحصاءات ولوحة مذكورة، دون مواصفات عرض مفصلة | **مهم** — تقويم إنجازات/فائت/استثناءات، مرشحات أسبوع/شهر/مدى مخصص، تصدير رسم/بيانات |
| ملاحظات ومزاج ومؤقت | توجد ملاحظات ومزاج في اليومية، لكن لا ملاحظات لكل إنجاز ومؤقت | **لاحق** — ملاحظة يومية لكل عادة؛ مؤقت/عداد للمدة والكمية |
| تتبع آلي عبر الصحة/الأجهزة أو تطبيقات أخرى | غير موجود | **لاحق واختياري** — تكاملات بموافقة المستخدم، مع مراجعة/تصحيح القيمة قبل اعتمادها. لا تربطها افتراضيًا |
| مزامنة بين الأجهزة والعمل بلا اتصال | غير محدد | **أساسي عند تعدد الأجهزة** — مزامنة موثوقة، وضع Offline، معالجة تعارضات واضحة |
| تصدير ونسخ احتياطي | غير محدد | **أساسي** — تصدير CSV/JSON؛ نسخ احتياطي واستعادة مشفران إن توفر التخزين السحابي |
| خصوصية البيانات | عزل user_id مذكور؛ بقية الضوابط غير محددة | **أساسي** — صلاحيات على مستوى السجل، تشفير النقل/التخزين، وضوح سياسة الخصوصية، حذف الحساب وتصدير البيانات |
| قوالب جاهزة للعادات | غير موجود | **لاحق** — اقتراح قوالب قابلة للتعديل، لا تنشئ عادات دون موافقة المستخدم |
| وسوم ومجموعات/مجالات وروتينات | فئات للعادات موجودة | **لاحق** — وسوم ومجموعات اختيارية؛ لا تنشئ كيانًا مكررًا للمشاريع/المال/التعلّم |
| معالم وإنجازات وتشجيع | الإنجازات موجودة، لكن milestone/رسائل التقدم غير محددة | **مهم** — معالم قابلة للتخصيص مع خيارات إيقاف التشجيع/الرسوم المتحركة |
| نقاط قوة العادة بدل الاعتماد على السلسلة وحدها | سلاسل ونسب موجودة | **لاحق** — أضف مؤشر اتساق/قوة منفصلًا يشرح طريقته؛ لا تستبدل به الحسابات الواضحة |
| إمكانية الوصول وRTL | لا مواصفات | **أساسي** — دعم العربية واتجاه RTL، تكبير الخط، ألوان مناسبة لعمى الألوان، واستخدام لوحة المفاتيح وقارئات الشاشة |

### 19.1 ترتيب الأولويات المقترح

**إصدار أول (لازم لإطلاق موثوق):** الجدولة كاملة، تاريخ البداية/النهاية، توقف واستثناء، ضبط الكميات، Quick Log، إعادة الحساب بعد التعديل/الحذف، عزل المستخدمين، سجل تدقيق أساسي، تصدير البيانات، واجهة عربية/RTL إذا كانت العربية ضمن الجمهور.

**إصدار ثانٍ:** تذكيرات متعددة، تقويم وتحليلات مفصلة، الملاحظات على سجل اليوم، أدوات الشاشة/الإشعارات التفاعلية، نسخ احتياطي ومزامنة متعددة الأجهزة.

**إصدارات لاحقة اختيارية:** تكاملات الصحة، المؤقتات، القوالب، التحديات/المشاركة، والاقتراحات الذكية. يجب أن تكون المشاركة/التكاملات اختيارية وموقوفة افتراضيًا لحماية الخصوصية.

---

## 20. حماية البيانات والخصوصية

1. كل قراءة أو كتابة أو حذف يجب أن تتحقق من `user_id` على الخادم/قاعدة البيانات؛ إخفاء البيانات في الواجهة وحده غير كافٍ.
2. يوميات المستخدم خاصة افتراضيًا، ولا تُشارك مع مستخدمين آخرين أو تكامل خارجي دون اختيار صريح.
3. استخدم تشفير النقل، وتشفير التخزين حيث تدعمه البنية، وصلاحيات أقل امتيازًا، وسجلات تدقيق لعمليات الحذف والتغييرات الحساسة دون تسجيل نص اليوميات في سجلات التشغيل.
4. وفّر تنزيل بيانات المستخدم بصيغة مناسبة (JSON كاملة وCSV للسجلات)، مع تاريخ التصدير والمنطقة الزمنية ومعاني الحالات.
5. عرّف آلية النسخ الاحتياطي والاستعادة، ومدة الاحتفاظ، وطريقة حذف النسخ بعد طلب الحذف النهائي. لا تعد بميزة نسخ احتياطي سحابي قبل تحديد مكان التشفير ومفاتيحه وصلاحياته.
6. لا ترسل بيانات صحية أو يوميات إلى أي تكامل أو نموذج خارجي إلا بعد إبلاغ المستخدم والحصول على موافقته اللازمة.
7. أضف صفحة إعدادات الخصوصية: التصدير، إدارة التذكيرات والتكاملات، استعادة المحذوفات، وطلب حذف الحساب.

## 21. اختبارات قبول إضافية

أضف الاختبارات التالية إلى اختبارات القبول الأصلية:

15. عادة كل يومين تُنتج مواعيد متوقعة من تاريخ البداية، ولا تعد الأيام البينية إخفاقًا.
16. عادة الاثنين/الأربعاء/الجمعة لا تنكسر سلسلتها يوم الثلاثاء إذا كان غير مجدول.
17. عادة 3 مرات أسبوعيًا تُحسب على بداية الأسبوع المحددة للمستخدم، ولا تُحكم الفترة قبل انتهائها.
18. الهدف الشهري في شهر لا يحتوي اليوم المطلوب يتبع قاعدة الشهر المختارة بصورة ثابتة.
19. لا ينشأ إخفاق للموعد قبل نهاية اليوم/الفترة حسب المنطقة الزمنية للمستخدم.
20. تاريخ نهاية العادة شامل؛ لا تتولد مواعيد بعده، و`end_date = null` يعني استمرارها.
21. الإجازة والتخطي لا يُحسبان نجاحًا، ولا يقطعان السلسلة، ولا يضافان إلى مقام الالتزام.
22. الإيقاف المؤقت يستثني فترة الإيقاف، والاستئناف لا يغير التاريخ السابق.
23. `actual >= goal` ينتج Done؛ والكمية بين الحد الأدنى والهدف تنتج Partial؛ وما دون الحد الأدنى يفشل عند إغلاق الموعد.
24. تعديل الهدف أو الجدول بتاريخ سريان جديد لا يغيّر الحساب التاريخي قبل ذلك التاريخ.
25. حذف/تعديل سجل يوم قديم يعيد حساب السلسلة والإنجازات ذات الصلة مرة واحدة وبشكل صحيح.
26. تعديل/حذف انتكاسة قديمة يعيد حساب clean days وأفضل سلسلة تاريخية دون فقدان التاريخ الصحيح.
27. أرشفة عادة لا تحذف السجلات، والحذف النهائي لا يقع دون اختيار واضح لأثره على البيانات المرتبطة.
28. حذف كتاب لا يحذف Daily Logs؛ ويُزال رابط الكتاب فقط.
29. المستخدم لا يستطيع قراءة أو تعديل أو حذف سجل تابع لمستخدم آخر بتغيير المعرّف.
30. تصدير البيانات يشمل السجلات والعلاقات والتواريخ والحالات، ولا يكشف بيانات مستخدم آخر.
31. دعم العربية وRTL لا يعكس ترتيب التاريخ أو الأرقام بطريقة تخالف قيمة البيانات المحفوظة.
32. تكرار إرسال Quick Log لا ينشئ سجلين؛ يكون الإدخال idempotent.

## 22. تغييرات مباشرة على الملف الأصلي

لتطبيق هذا الملحق على المواصفات الحالية:

1. في جدول حقول Habit بالقسم 4، أضف `tracking_type`, `start_date`, `end_date`, `timezone`، وقواعد الجدولة المنظّمة، والنسخ المؤرخة للهدف والجدول.
2. في حالات Daily Log بالقسم 5، وثّق الفرق بين `Vacation`, `Skipped/Excused`, و`Missed`، وطبّق قواعد الفترة المجدولة من القسم 16.
3. في قسم الحسابات، استبدل معنى السلسلة العامة بقواعد المواعيد/الفترات، مع إبقاء عدم إنشاء سجلات يومية تلقائيًا.
4. أضف قسمًا عامًا للإضافة والتعديل والأرشفة والحذف يطبق جدول القسم 17 على كل الكيانات.
5. أضف الإعدادات الافتراضية واختبارات القبول من القسمين 18 و21.
6. نفّذ الأولويات من القسم 19.1؛ لا تبدأ بالتكاملات أو الميزات الاجتماعية قبل ثبات الجدولة والبيانات والخصوصية.
