# Home OS — المرحلة الأولى: معايير القبول

الحالة: تنفيذ أولي على فرع تطوير؛ غير مدمج وغير منشور للإنتاج.

## ما نُفّذ في الفرع
- إضافة وحدة Home OS ضمن عقد تحميل الأنظمة الحالي في `src/systems/home/index.jsx`.
- شاشة رئيسية بمؤشرات أولية، وإدارة العقارات والغرف والمخزون.
- إنشاء الغرفة النظامية «عام / البيت كله» لكل عقار.
- أنواع عناصر المخزون، والفئة والوحدة والكمية والحد الأدنى والسعر والشراء والضمان والصلاحية والموديل والرقم التسلسلي والملاحظات.
- حركات مخزون أولية: استلام، استهلاك، تسوية، والتخلص؛ مع سجل حركة ومفتاح idempotency.
- حالات مشتقة للمخزون، والضمان، ومؤشرات صحة الغرفة.
- طبقة domain/repository واختبارات لها.
- Migration منفصلة لبيانات Home OS وجداول العقارات والغرف والمخزون والحركات والإعدادات وسجل التدقيق، مع RLS وRPC snapshot.
- ربط repository بـ RPCs المعيارية، مع fallback مؤقت حتى تكون migration مطبقة ومتحققًا منها.
- أضيفت واجهات المهام المنزلية والتكرار والصيانة والمشتريات الجزئية والفواتير ومقدمي الخدمات والتقارير في المرحلة التشغيلية الثانية.
- أضيفت اختبارات domain لحساب الاستحقاقات الدورية وتواريخ نهاية الشهر والسنة الكبيسة، وحالات الاستلام الجزئي.
- أُضيف تكامل أحداث محلي: إنجاز المهام يظهر في Today، ودفع الفواتير يفتح اقتراح تسجيل مصروف في Finance للمراجعة والتأكيد.

## اختبارات القبول
1. لا يُحفظ عقار بلا اسم.
2. لا تُحفظ غرفة بلا اسم أو مرتبطة بعقار غير موجود.
3. لا يُحفظ عنصر بكمية أو حد أدنى سالب.
4. لا يُصرف من المخزون أكثر من الكمية المتاحة.
5. لا تنتج حركة مخزون رصيدًا سالبًا.
6. حركة الاستلام تزيد الرصيد، والاستهلاك/التخلص ينقصه، والتسوية تستبدله بالقيمة المحددة.
7. يحسب النظام حالة المخزون من الكمية والحد الأدنى، لا من حقل يدوي.
8. لا يُحسب المؤرشف ضمن مؤشرات المخزون أو الغرف.
9. تبقى حركات العنصر المؤرشف محفوظة تاريخيًا.
10. لا تقبل طبقة repository غرفًا بعقار غير موجود أو حركات بعنصر غير موجود.
11. تُعزل بيانات مساحة العمل بواسطة RLS وRPC.
12. لا يملك دور anon صلاحيات على جداول Home.
13. تُرفض الكتابة إلى RPC دون مستوى edit.
14. إعادة إرسال حركة بنفس idempotency key لا تضيف حركة ثانية.

## ما لم يُعتمد بعد
- لا تُطبّق migration على Supabase الإنتاجية من هذا الفرع.
- لم يتم بعد إثبات browser acceptance على Preview.
- واجهات العمليات موجودة، لكن لا تزال تحتاج اختبارات متصفح وقبول end-to-end على آخر head.
- لا يُنشأ دفتر مالي داخل Home OS. تكامل دفع الفاتورة الحالي حدث محلي best-effort؛ ليس مزامنة خادمية موثوقة بين الأجهزة، وتكاليف الصيانة والمشتريات لم ترتبط بعد بمراجعة Finance.
- نجحت CI (ESLint + npm test + production build) ونجح اختبار PostgreSQL المعزول لتطبيق migrations والتحقق من snapshot/RLS وidempotency على head ‏ed51d64879e84e10d22a1ed1c0fcf522a152e0a6. لا يزال اعتماد القسم النهائي متوقفًا على browser acceptance، وحسم ازدواج snapshot والجداول العلائقية، وإعادة التحقق بعد أي تعديل لاحق للكود.
- يجب تشغيل migration في PostgreSQL/Supabase معزول والتحقق من سياسات RLS وRPC قبل أي نشر.

## ملاحظة معمارية
وحدة الواجهة تعتمد repository؛ عند توفر RPCs المعيارية تستخدم الجداول المخصصة. في البيئات التي لم تطبق migration بعد، يوجد fallback مؤقت إلى API مساحة العمل الحالية. يجب إزالة هذا الـ fallback بعد ترحيل البيانات والتحقق من البيئة المستهدفة.

## تحديث مراجعة الفيتشرز — 2026-10-31
- **مكتمل على مستوى الواجهة/الكود:** العقارات والغرف والمخزون، الحركات، المهام، التكرار، الصيانة، مقدمو الخدمة، طلبات شراء مع استلام جزئي، الفواتير الدورية، التقارير، وأحداث Today/Finance المحلية.
- **غير مكتمل للاعتماد:** مصدر حقيقة عمليات المنزل ما زال JSON snapshot مع وجود جداول relational موازية غير مستخدمة من الواجهة؛ أحداث التكامل محلية فقط؛ لا تعيين أعضاء المنزل ولا push/background reminders؛ لا تكامل مالي لتكاليف الصيانة/المشتريات؛ لا اختبار متصفح أو Supabase معزول خاص بـ Home OS.
- **التحقق:** أُضيف lint إلى CI، وكشف 80 استدعاءً للمكوّن Field بحروف صغيرة في Shopping OS؛ تم إصلاحها، ثم نجح ESLint وnpm test وproduction build على head المذكور. Vercel Preview ما زال محدودًا بسبب build-rate-limit على مستوى الحساب، وهو منفصل عن نجاح build داخل CI.
