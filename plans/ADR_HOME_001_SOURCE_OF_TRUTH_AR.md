# ADR-HOME-001 — مصدر الحقيقة لبيانات Home OS

- الحالة: Accepted for implementation in the Home OS phase-2 draft; not yet production-deployed.
- التاريخ: 2026-10-31
- النطاق: المهام المنزلية، الصيانة، طلبات الشراء وبنودها والاستلامات، الفواتير الدورية، مقدمو الخدمات، وحركات المخزون المرتبطة.
- القرار: **الجداول العلائقية في PostgreSQL/Supabase هي مصدر الحقيقة الوحيد للبيانات التشغيلية في Home OS.** لا يجوز أن تحفظ الواجهة snapshot كاملًا لهذه الكيانات في `workspace_data` أو `localStorage` باعتباره نسخة قابلة للكتابة وموازية للجداول.

## لماذا هذا القرار؟

1. تحتاج عمليات الاستلام الجزئي وحركات المخزون إلى معاملات ذرية وقيود uniqueness تمنع التكرار.
2. الحفظ المتزامن من أكثر من جلسة يحتاج optimistic concurrency أو عمليات RPC ذرية، لا استبدال JSON كامل قد يمحو تحديث جلسة أخرى.
3. العلاقات والقيود المرجعية والتقارير والصلاحيات أدق في الجداول العلائقية.
4. أحداث Finance وToday تحتاج أن تُنشأ في نفس معاملة تغيير Home عبر outbox دائم، بدل أحداث المتصفح التي قد تضيع.
5. هذا يطابق الحاجة إلى استعلامات وتقارير وصلاحيات على مستوى العقار والغرفة، مع فصل صلاحيات القراءة والكتابة.

## حدود JSON

- يُسمح بـ JSONB للحقول المرنة ذات الطبيعة الوصفية أو إعدادات واجهة غير معاملية، بشرط أن تكون ملكيتها واضحة.
- لا يُسمح بتخزين نسخة قابلة للكتابة من المهام أو الطلبات أو بنودها أو الاستلامات أو الفواتير أو حركات المخزون داخل snapshot.
- لا تُعد `localStorage` مصدرًا دائمًا أو مرجعًا نهائيًا. يمكن استخدامه لتفضيلات واجهة أو cache قابل لإعادة البناء فقط.

## نموذج البيانات المستهدف

- `home_properties` و`home_rooms`: العقارات والغرف أو مرجع موثوق إلى الجداول الحالية إن كانت موجودة؛ يمنع إنشاء كيان مكرر.
- `home_tasks` و`home_task_occurrences`: تعريف المهمة وتكرار/إنجاز كل occurrence.
- `home_maintenance`: سجلات الصيانة وتكلفتها وحالتها.
- `home_purchase_orders` و`home_purchase_order_items`: الطلب وبنوده وكمياته وأسعاره وحالاته.
- `home_purchase_receipts`: سجل append-only لكل دفعة استلام مع مفتاح idempotency فريد.
- `home_inventory_movements`: دفتر حركات مخزون append-only؛ كل استلام ينشئ حركة واحدة فقط داخل المعاملة نفسها.
- `home_bills` و`home_bill_occurrences`: تعريف الفاتورة الدورية ودورات الاستحقاق/الدفع.
- `home_service_providers`: مقدمو الخدمة.
- `home_outbox_events`: أحداث دائمة لـ Finance وToday مع `event_id` و`workspace_id` و`aggregate_type` و`aggregate_id` و`event_type` و`payload` و`idempotency_key` و`created_at` و`published_at` و`attempt_count` و`last_error`.

قبل كتابة migration يجب فحص المخطط الحالي وإعادة استخدام الجداول القائمة بدل إنشاء نسخ متوازية. أسماء الجداول أعلاه أسماء مستهدفة توضيحية، وليست تصريحًا بإنشاء كل جدول دون فحص.

## قواعد الاتساق

- تغيير الحالة، إنشاء الاستلام، تعديل الكميات المتبقية، إنشاء حركة المخزون، وإنشاء أحداث outbox عملية ذرية واحدة.
- المفتاح الفريد للاستلام يحدد حدث الاستلام/الطلب/البند/دفعة العميل، ولا يُشتق من قيمة كمية قابلة للتغير فقط.
- يُمنع تحديث أو حذف حركات المخزون السابقة؛ التصحيح يكون بحركة عكسية موثقة.
- لا تُنشأ معاملة مالية نهائية تلقائيًا؛ يُنشأ اقتراح مالي دائم للمراجعة البشرية، ثم يؤكد المستخدم الحساب والتصنيف.
- أحداث Today لا تنقل ملكية المهمة؛ هي إسقاط/إشعار مشتق من الحدث الدائم.
- أي عملية كتابة تتحقق خادميًا من عضوية workspace والصلاحية على العقار/الغرفة، ولا تثق في `user_id` يرسله العميل.
- كل جدول مكشوف عبر Data API يخضع إلى RLS وسياسات ملكية/عضوية صريحة، مع اختبارات لمستخدمين من مساحات عمل مختلفة.

## خطة الانتقال دون فقد بيانات

1. جرد migrations والجداول وواجهات repository وحقول snapshot الحالية، وتحديد مصدر البيانات الفعلي لكل كيان.
2. إعداد migration توافقية في الفرع فقط، وعدم تطبيقها على مشروع الإنتاج.
3. إضافة repository علائقي وRPCs ذرية، ثم تحويل القراءة والكتابة تدريجيًا خلف واجهة repository موحدة.
4. إنشاء أداة ترحيل idempotent من snapshot القديمة إن وُجدت بيانات Home فعلية: validate → dry-run/report → import → count/hash reconciliation.
5. خلال فترة الانتقال، يسمح بقراءة legacy فقط عند الحاجة، ويُمنع dual-write. بعد تحقق الأعداد والعلاقات، تعطيل مسار snapshot للكيانات التشغيلية.
6. اختبار الاستلام الجزئي وإعادة المحاولة المتزامنة، التحديث المتعارض، RLS، reload/session جديدة، وتدفق outbox.
7. فقط بعد اجتياز الاختبارات في بيئة معزولة، تجهيز migration للنشر ومراجعتها. لا نشر ولا migration إنتاجية ضمن هذه المرحلة.

## بوابة القبول

- لا يوجد مساران للكتابة للكيانات التشغيلية.
- استلام واحد يُنتج سجل استلام وحركة مخزون وحدث outbox واحدًا حتى مع إعادة المحاولة والتزامن.
- لا تُفقد تحديثات جلستين؛ تعارض النسخ يُرفض برسالة قابلة للمعالجة أو يُحل عبر RPC ذري.
- Finance/Today يستهلكان الأحداث الدائمة بشكل idempotent.
- سياسات RLS واختبارات view/edit واختبار مستخدم من workspace آخر كلها ناجحة.
- توثيق نتائج dry-run والمصالحة قبل حذف أو تعطيل أي مسار legacy.
